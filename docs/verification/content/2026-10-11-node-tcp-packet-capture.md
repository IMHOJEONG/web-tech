# Node.js 로컬 TCP 캡처 재실행과 로그 대조

## 대상과 조건

- 검토 날짜: 2026-10-11 Asia/Seoul. 사용자 로컬 터미널에서 실행한 로그를 검토했습니다.
- 저장소 기준: `9c84c9d`의 미커밋 작업 트리. 커밋·배포 식별자가 아니라 검토 기준입니다.
- 도구: macOS 루프백 `lo0`, Node.js v24.12.0, tcpdump 4.99.1 / Apple 158 / libpcap 1.10.1.
- 대상: 기존 소켓 MDX를 추출하는 로컬 실험실의 연결 대기 도구와 sudo tcpdump.
- 범위: 같은 컴퓨터·단일 IPv4 HTTP/1.1 연결. 브라우저·TLS·Vercel 운영 경로는 대상 밖입니다.

## 재현 방법

[로컬 소켓·패킷 재현 절차](../../runbooks/node-tcp-local-observation.md)를 따릅니다.
사용자가 관리자 비밀번호를 자신의 터미널에서 입력합니다. 인증 정보는 수집하지 않습니다.
소켓 출력은 `/tmp/heapforge-socket-run.txt`, 캡처 텍스트는
`/tmp/heapforge-tcp-capture.txt`에서 읽었습니다.

캡처 안내를 `-l`과 `2>&1 | tee -i`를 포함하도록 수정했습니다.
`node scripts/socket-packet-capture.mts --auto-release`의 종료 코드 0으로 연결 대기·실행·종료를
재확인했습니다. 이 smoke는 sudo나 패킷 수집을 수행하지 않은 별도 검사입니다.

### 최종 캡처의 12행 해석

관측 구간은 **2026-10-11 14:12:37.706212~14:12:37.755922 Asia/Seoul**입니다.
C는 `127.0.0.1:60187`, S는 `127.0.0.1:60116`입니다.
아래는 실제 로그를 읽기 쉽게 정리한 표이며 원문은 별도 artifact에 있습니다.
`seq a:b`의 b는 범위에 포함되지 않습니다. `—`는 원문에서 그 필드를 출력하지 않은 경우입니다.

| 행  | 방향  | Flags | seq                   | ack        | TCP 데이터 길이 | 해석                                                          |
| --- | ----- | ----- | --------------------- | ---------- | --------------- | ------------------------------------------------------------- |
| 1   | C → S | S     | 197459810             | —          | 0               | 클라이언트 시작 번호를 알립니다                               |
| 2   | S → C | S.    | 1070684333            | 197459811  | 0               | 서버 시작 번호와 클라이언트 SYN 확인입니다                    |
| 3   | C → S | .     | —                     | 1070684334 | 0               | 서버 SYN을 확인합니다                                         |
| 4   | S → C | .     | —                     | 197459811  | 0               | 추가 ACK가 관측됐습니다. 발생 이유는 별도 계측하지 않았습니다 |
| 5   | C → S | P.    | 197459811:197459871   | 1070684334 | 60              | 클라이언트 방향의 HTTP 요청 바이트입니다                      |
| 6   | S → C | .     | —                     | 197459871  | 0               | 요청 60바이트의 다음 기대 번호를 알립니다                     |
| 7   | S → C | P.    | 1070684334:1070684470 | 197459871  | 136             | 서버 방향의 HTTP 응답 바이트입니다                            |
| 8   | C → S | .     | —                     | 1070684470 | 0               | 응답 136바이트의 다음 기대 번호를 알립니다                    |
| 9   | S → C | F.    | 1070684470            | 197459871  | 0               | 서버 방향에서 더 보낼 바이트가 없음을 알립니다                |
| 10  | C → S | .     | —                     | 1070684471 | 0               | 서버 FIN이 차지하는 번호 하나까지 확인합니다                  |
| 11  | C → S | F.    | 197459871             | 1070684471 | 0               | 클라이언트 방향의 송신 종료입니다                             |
| 12  | S → C | .     | —                     | 197459872  | 0               | 클라이언트 FIN을 확인합니다                                   |

실제 필드로 다음을 프로그램에서 검증했습니다.

- SYN 확인: `197459810 + 1 = 197459811`, `1070684333 + 1 = 1070684334`.
- 요청 범위: `197459871 - 197459811 = 60`. 다음 서버 ACK도 `197459871`입니다.
- 응답 범위: `1070684470 - 1070684334 = 136`. 다음 클라이언트 ACK도 `1070684470`입니다.
- 서버 FIN 확인: `1070684470 + 1 = 1070684471`.
- 클라이언트 FIN 확인: `197459871 + 1 = 197459872`.
- 모든 패킷의 끝점이 같은 실행의 소켓 JSON과 일치하며, 캡처 12행에서 RST는 관측되지 않았습니다.
- 정리한 소켓 결과는 연결 1개, HTTP 200, 본문 15바이트, complete true입니다.

본문 `hello from TCP\n`는 **소켓 JSON에서 확인한 문자열**입니다.
패킷 로그는 원문 본문을 출력하지 않으므로 60·136바이트 자체를 읽어 본문 내용을
확인했다고 주장하지 않습니다. 단일 실험의 요청·응답 방향과 길이는 서로 연결해 해석합니다.
현재 한 표본에서는 요청과 응답이 각각 데이터 세그먼트 하나였지만 항상 그렇지는 않습니다.

### 종료 집계와 시간 해석

```text
12 packets captured
58 packets received by filter
0 packets dropped by kernel
```

12개의 출력 행과 captured 12가 일치합니다. 커널 drop은 0으로 보고됐습니다.
received by filter의 의미는 OS·수집 경로에 따라 다르므로 captured와 같아야 한다고
요구하지 않습니다. `58 - 12 = 46`을 패킷 유실로 해석할 근거는 없습니다.
SYN·양방향 데이터·양방향 FIN 확인·최종 ACK가 모두 있어 **이번 한 연결의 정상적인
설정과 종료 흐름을 캡처했다**고 판정합니다. 다른 연결이나 캡처 구간 밖까지 확장하지 않습니다.

첫 SYN부터 마지막 ACK까지의 로그상 차이는 49.710ms입니다. 요청 데이터 행부터
응답 데이터 행까지는 43.501ms입니다. 서버 처리 함수가 동기 `lsof` 조회를 실행하므로
이 차이를 네트워크 지연·실제 HTTP 서비스 성능·순수 RTT로 해석하지 않습니다.
커널 함수 시각이나 Node.js 이벤트와 동기화한 정밀 계측은 하지 않았습니다.

## 한계와 후속 작업

최초 불완전 파일만으로 패킷을 분석하지 않았습니다. 최종 캡처를 별도로 확보해 판정했습니다.
`listening on lo0`만으로 수집 성공을 판단하지 않으며 패킷·종료 집계까지 대조합니다.
표본은 한 개입니다. 커널 내부 함수·복사 횟수·버퍼의 실제 할당 크기·TIME_WAIT 상태를
직접 계측하지 않았습니다. 루프백 BPF 관측을 물리 네트워크 전송 형태로 일반화하지 않습니다.
캡처 개념과 가상 번호는 학습 문서에, 날짜별 실제 숫자는 이 보고서에 유지합니다.
스테이징·커밋·푸시·원격 게시를 수행하지 않았습니다.
