### 같은 날 추가 보강 검토

사용자의 추가 분석 요청으로 세 에이전트가 최종 원문을 다시 읽었습니다. 아래는 편집 후보이며 본문·예제·도식에 아직 반영하지 않았습니다. 추가 실행·패킷 캡처는 수행하지 않았고 앞선 통과 결과를 새 실험의 성공으로 확장하지 않습니다.

| 우선순위 | 보강 후보                             | 독자에게 필요한 이유와 권장 분량                                                                                                                                                                                                 |
| -------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1        | HTTP 메시지 완료와 TCP 연결 종료 구분 | 결과의 `complete`·`connections`를 풀고 `Connection: close`라는 조건을 코드 밖에 표시합니다. `complete`는 온전한 HTTP 메시지 수신·파싱이며 FIN·소켓 close·화면 표시 완료와 다릅니다. 결과 아래 짧은 설명이나 비교표가 적절합니다. |
| 2        | 서버 포트 공유와 연결 구분            | 연결 수락 뒤 대기 소켓은 계속 기다린다는 한 문장과 `(내 주소, 내 포트, 상대 주소, 상대 포트)` 조합을 풉니다. 두 클라이언트가 같은 서버 포트에 연결하는 표는 가상 예시임을 표시하며 현재의 단일 연결 실측과 분리해야 합니다.      |
| 3        | 관측 결과를 스스로 읽는 연습          | 서버·클라이언트 포트가 출력 어디에 반복되는지, 한 연결에서 ESTABLISHED 두 행이 나타나는 이유, 본문 완료를 확인한 증거를 묻는 짧은 문항을 둡니다. 기존 해설과 교체해 반복을 줄입니다.                                             |
| 4        | 패킷 재현의 독립성                    | 공개 코드만으로 소켓 관측은 재현되지만, 패킷 캡처의 대기·시작 절차는 공개 본문에 없습니다. 선택형 캡처 안내를 보강하려면 독자가 그대로 쓸 수 있는 대기 단계와 동적 포트 안내를 제공하고 원문 바인딩·실험을 다시 검증해야 합니다. |

별도 실험 후보는 HTTP/1.1 keep-alive입니다. 한 연결에서 순차 요청 두 개를 끝까지 소비하고 연결 수 1·응답별 완료·동일 끝점 재사용을 확인하는 설계입니다. 마지막 연결 종료와 FIN 관측은 별도 증거가 필요합니다. 이번에는 설계 제안만 했습니다. CPU·TCP 윈도우·재전송·TIME_WAIT까지 이번 본문에 함께 늘리지 않는 편을 권합니다.

편집 관점에서는 패킷 도식과 순서가 겹치는 표를 접어 새 설명의 분량을 확보할 수 있습니다. ACK·캡처 한계의 핵심 경고는 그림 옆에 남기고 세부 기록만 접는 편이 안전합니다. 이 판단은 새 독자 사용성 실험이 아닌 원문 검토입니다.

공식 근거를 다시 확인했습니다: [Node.js HTTP 메시지 완료](https://nodejs.org/download/release/v24.12.0/docs/api/http.html#messagecomplete), [연결 재사용을 관리하는 Agent](https://nodejs.org/download/release/v24.12.0/docs/api/http.html#class-httpagent), [TCP 연결을 구성하는 소켓 쌍](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2). 실제 글에 넣을 때는 확인된 개념과 추가 실험 결과를 구분합니다.

### 보강 반영과 선택형 캡처 대기 검사

사용자가 위 보강안의 반영을 요청해 네 항목을 적용했습니다. 두 연결의 같은 서버 포트와 다른 상대 포트는 가상 비교표이며, 실제 소켓·패킷 결과로 표시하지 않았습니다. 결과 아래에 `complete`·응답 `end`·TCP FIN·소켓 `close` 비교와 HTTP/1.1·`Connection: close` 조건을 추가했습니다. 본문에 노출된 핵심 설명을 유지하고 반복 패킷 표를 접었으며, 확인 문제 세 개와 접힌 답을 넣었습니다.

선택형 캡처는 외부 전용 도구 없이 공개 `.mts` 한 파일로 시작할 수 있습니다. 원문 3/5 블록의 `CAPTURE_TCP=1` 분기는 listen 완료 후 실제 포트를 넣은 tcpdump 명령을 출력하고 Enter를 기다립니다. 일반 실행은 기다리지 않습니다. `sudo`는 안내 문자열로만 출력하며 프로그램이나 자동 테스트에서 실행하지 않습니다. 실패·취소 시 A도 Ctrl+C로 종료하는 절차를 넣었습니다.

실험실의 `scripts/tcp-socket-endpoints.mts`를 실제 MDX 추출 결과로 맞추고 `scripts/socket-article-source.test.mts`에 대기 모드의 정식 검사를 추가했습니다. fixture와 원문 각각에서 Enter 전 LISTEN 1·ESTABLISHED 0, 출력 필터와 실제 대기 포트 일치, Enter 후 연결 1·HTTP 200·전체 본문·complete true를 검사합니다. 기존 일반 실행 각 3회·strict 타입·원문 누락과 순서 오류 거부 검사도 유지합니다.

- [보강 후 콘텐츠 검사](../artifacts/2026-10-16-tcp-enrichment-content.txt): frontmatter·스타일 19개 파일 통과.

기술·독자 이해·존댓말을 세 에이전트가 재검토했습니다. 기술·구성에서 필수 수정은 없었고, 수락 용어와 자가 점검의 서버 연결 local/remote 표기, 캡처 실패 시 종료 문장을 보완했습니다. 이는 실제 독자 대상 평가가 아닌 원문 검토입니다. 패킷 그림은 바꾸지 않았고 keep-alive 실험도 실행하지 않았습니다. 기존 패킷 캡처 대기 래퍼는 계속 기본 예제를 사용하므로 동작 경로를 변경하지 않았습니다.

보강 뒤 사용자가 확인 문제와 질문형 구성을 원하지 않는다고 알려 확인 문제·정답 전체를 제거했습니다. 도입과 소제목·접기 제목은 설명형으로 정리했습니다. 기술 설명·코드 다섯 블록·도식은 그대로입니다. 이전 절의 문제·정답 검사 결과는 당시 버전의 이력이며 현재 본문에 해당 영역이 남아 있다는 뜻이 아닙니다.

사용자 요청에 따라 마지막 절을 세 문단의 요약과 다음 글 예고로 정리했습니다. [10월 11일 실제 CPU 실험](2026-10-11-node-event-loop-cpu.md)의 각 3회 결과만 사용했습니다. 타이머 실행 약 20/200ms, 양쪽 16,384바이트·동일 내용, 콜백 실행 시각과 패킷 도착 시각의 구분을 반영했습니다. 독립 프로세스 코드와 시간 흐름도는 후속 글에서 다루도록 남겼으며 아직 없는 공개 링크를 만들지 않았습니다.
