# 페이지별 스켈레톤의 로컬 검증

## 대상과 조건

- 날짜: 2026-10-19 Asia/Seoul. `feature/docs`의 미커밋 작업 트리. 기준 HEAD는 artifact에 기록한다.
- 환경: 로컬 Next development 서버 `http://127.0.0.1:3011`, 원격 인덱스 비활성화. 운영 배포와 같은 조건의 성능 측정은 아니다.
- Chromium 390×844 ko, 768×1024 en, 1280×800 ko에서 밝은/어두운 테마와 모션 줄이기를 검사한다. 복합 필터는 각 프로젝트에서 320×844로 변경한다. 언어×모든 화면의 완전한 교차 표본은 아니다.
- 문서 목록·태그 검색·복합 필터·피드·Web·Mobile·UI/UX·카테고리 세 단계·상세의 11화면 × 두 테마 × 세 프로젝트로 골격 좌표 66표본을 비교한다. 홈의 부분 로딩 경계는 세 프로젝트에서 별도 검사한다.

## 재현 방법

저장소 루트에서 실행한다. 기존 3011 서버를 재사용한다면 원격 인덱스가 꺼진 로컬 전용 설정인지 먼저 확인한다.

```bash
DOCS_E2E_PORT=3011 mise exec -- pnpm --filter docs test:e2e page-skeletons docs-index-order docs-index-navigation search-navigation feed-lead-story feed-recent-articles hub-topic-filters uiux-compact-cards --project=chromium-mobile --project=chromium-desktop --project=chromium-tablet --workers=2
mise exec -- pnpm --filter docs typecheck
mise exec -- pnpm --filter docs lint
mise exec -- pnpm validate:docs
git diff --check
```

`page-skeletons.spec.ts`는 먼저 실제 서버 응답에 해당 도메인의 로딩 마크업이 포함되는지 확인하고 실제 페이지가 완성되는 것도 기다린다. 이후 그 응답에서 골격을 추출해 **테스트 브라우저 안에서만** 본문 자리에 고정하고 좌표·상태 안내·모션·화면 넘침을 비교한다. React가 빠르게 제거하는 골격의 모양을 재현하기 위한 기하 검사이며 실제 시간축의 전환·네트워크 지연·CLS 측정은 아니다. 앱에는 테스트 라우트나 지연을 추가하지 않았다.

## 결과와 증거

최종 실행 결과와 수치는 [검증 artifact](../artifacts/2026-10-19-page-skeletons-local.json)에 보관한다. 아래 차이는 `스켈레톤 앵커 top - 완성 화면 앵커 top`의 CSS pixel이며, 완성 화면의 글자·이미지 전체가 동일한 크기라는 뜻이 아니다.

| 화면                                | 비교한 위치         | 관측 차이        |
| ----------------------------------- | ------------------- | ---------------- |
| `/docs`, 태그 검색, 320px 복합 필터 | 결과 영역 시작      | 0px              |
| 피드·UI/UX                          | 첫 가로형 카드 시작 | 0px              |
| Web·Mobile                          | 허브 헤더 시작      | 0px              |
| 카테고리 목록·주제 목록             | 결과 섹션 시작      | 0px              |
| 하위 카테고리 문서 목록             | 결과 섹션 시작      | -8 / -28 / -48px |
| 상세                                | 본문 열 시작        | 0px              |

하위 카테고리 차이는 최근 문서 제목과 날짜가 들어가는 통계 카드의 실제 높이를 조회 전에 알 수 없어 생긴다. 음수는 스켈레톤의 목록 시작이 그만큼 위에 있음을 뜻한다. 허브는 헤더만 비교했으며 미확정 필터 줄 수와 카드 목록 시작점까지 0px라고 판정하지 않았다.

상태 안내의 존재, 장식 막대의 화면 넘침 없음, reduced motion에서 애니메이션 없음, 완성 화면과 본문 열의 좌측·폭 일치를 함께 검사한다. 홈은 소개 제목이 최근 글 로딩보다 먼저 응답에 포함되고, 실제 화면에서는 로딩 표시가 사라지는 것을 확인한다.

### 검사 중 발견과 조치

1. 초기 검사에서는 하위 카테고리가 상위 골격을 보내는 동작을 발견했다. 카테고리 loading 상속 대신 페이지별 `Suspense`로 수정했다. 검색 폼의 빈 상태 안내까지 페이지 로딩 안내로 세는 선택자와 데이터가 없어야 정상인 제목 기대값도 보완했다. 이후 초기 범위 33개는 통과했다.
2. 범위를 확장한 192개 실행에서는 174개 통과·6개 실패·12개 제외였다. 실패는 320px 복합 필터의 시작점 4px 차이였다. 필터 바 자체를 실제 화면과 공유하고 결과 수만 `…`로 표시하도록 수정했다.
3. 다음 126개 실행에서는 골격 검사 69개가 모두 통과했지만 기존 필터 검사 3개가 실패했다. 스트리밍의 숨겨진 다음 트리까지 선택한 것이 원인이었다. `:visible`로 범위를 좁히고 보이는 필터가 정확히 하나인지 확인하도록 도우미를 보완했다. 이 실행의 전체 결과는 117개 통과·3개 실패·6개 제외이며 최종 통과 결과로 바꿔 기록하지 않는다.
4. 도우미만 수정한 192개 재검사에서는 테스트 안의 직접 클릭·포커스 선택자가 남아 6개가 실패했다. 모든 필터 조작 선택자에 같은 visible 규칙을 적용했다. 관련 범위 재검사는 21개 통과·6개 조건부 제외·실패 0이었다.

### 최종 재검사

| 검사                              | 결과                                       |
| --------------------------------- | ------------------------------------------ |
| 관련 E2E 전체 192개               | 180개 통과·12개 조건부 제외·실패 0·flaky 0 |
| 위 실행에 포함된 페이지별 골격    | 좌표 66표본 + 홈 경계 3개, 모두 통과       |
| TypeScript·docs lint              | 통과                                       |
| 문서 변경 검사·`git diff --check` | 통과                                       |

제외 12개는 기존 테스트의 프로젝트 조건이다. 문서 필터 이동 3개는 모바일에서만 실행하고, 별도의 너비 순회·카드 상호작용 검사는 데스크톱 프로젝트에서 실행해 다른 프로젝트의 중복을 제외한다. 제외된 테스트 이름·프로젝트는 artifact에 기록했으며 통과 수에 포함하지 않는다.

캡처는 테스트에서 고정한 서버 골격이며 실제로 느린 연결을 녹화한 것이 아니다.

## 한계와 후속 작업

2026-10-27에는 이 검사의 live React DOM 직접 교체가 늦은 hydration과 충돌하는 사례를 재현했다. 당시 결과는 그대로 보존하며 [격리 보완과 반복 검사](../resilience/2026-10-27-skeleton-runtime-isolation.md)를 후속 근거로 연결한다.

production build·공개 배포·실제 느린 연결·Safari/Firefox·실기기·스크린 리더·Web Vitals CLS는 미검증이다. `pageerror` 0은 모든 console 경고가 없다는 뜻이 아니다. 캡처의 Next 개발 표시기는 운영 UI가 아니다.

결과 수·빈 결과·제목 줄 수·필터 줄 수·이미지와 본문 길이에 따라 높이 차이는 남는다. 본문 전체나 푸터의 위치가 움직이지 않는다고 보장하지 않는다. 운영 전환에서 중요한 앵커가 계속 움직인다면 실제 데이터가 필요한 영역만 더 작은 경계로 나누는 후속 검토가 필요하다.
