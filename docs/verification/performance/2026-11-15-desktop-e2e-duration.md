# 데스크톱 E2E 소요 시간 조사

## 대상과 조건

- 조사일: 2026-11-15 KST. [KAN-78](https://web-tech-service.atlassian.net/browse/KAN-78).
- 소스 기준: main `3b5444edabe021dc18b62baa7e7060c9353c9c3a`. 최초 조사는 코드 변경 없이 수행했다. 이후 사용자 승인으로 같은 작업 트리에 선택적 계측·대조 도구·회귀 검사를 추가했다. CI·Playwright 설정·앱·의존성은 바꾸지 않았다.
- 비교: 성공한 main CI 3개에서 responsive 모바일·태블릿·데스크톱 job 9개를 읽었다. 실패 실행을 성공 실행과 섞어 평균 내지 않았다.
- 환경: 저장소의 Node 24.22.1·pnpm 12.14.0, Playwright 1.62.1 사전 설치 noble 이미지. 실제 list reporter는 모든 표본에서 worker 2개를 보고했다.
- 최초 원시 CI 로그는 메모리에서 분석했다. 초기 정제 집계는 비공개 임시 경로에 보관했고, 11-16 사용자 승인 후 직접 작성한 계측·회귀 코드와 운영 문서6개만 공개 검수·커밋·푸시했다. 독립 CI에는 엄격한 스키마의 합성 숫자·hash만 전달하며 원시 로그·trace·화면·실제 응답·자격 증명은 추가하지 않는다.

## 재현 방법

인증된 GitHub CLI에서 원본 실행의 job/step 시간과 reporter 결과를 확인한다. 아래 명령은 읽기 전용이며 원문 출력을 공개 문서나 artifact에 첨부하지 않는다.

```sh
gh run view 43595500214 --repo IMHOJEONG/web-tech --json headSha,jobs
gh run view 43595500214 --repo IMHOJEONG/web-tech --job 132448992525 --log
gh run view 43663220243 --repo IMHOJEONG/web-tech --json headSha,jobs
gh run view 43663220243 --repo IMHOJEONG/web-tech --job 132656890603 --log
gh run view 43384044485 --repo IMHOJEONG/web-tech --json headSha,jobs
```

측정 방식:

1. job의 `completedAt - startedAt`을 준비·정리를 포함한 전체 시간으로 사용한다.
2. `Run browser suite` step의 시작/종료 차이를 브라우저 명령 시간으로 사용한다. 서버 준비와 테스트가 함께 들어 있어 순수 assertion 시간은 아니다.
3. list reporter에서 프로젝트·테스트 이름·시간·retry 표시·최종 통과/skip을 추출한다. 원문 오류 메시지·실제 응답·인증 정보는 정제 집계에서 제외한다.
4. 파일별 시간은 **각 테스트의 보고 시간을 더한 worker 시간 합계**다. 병렬 실행이므로 벽시계 시간과 같지 않다. reporter의 반올림도 포함한다.
5. 동명 시나리오는 파일명/제목으로 연결하며 코드 행 번호는 제외한다. 화면 크기·조건 분기와 실행기의 부하 차이가 있으므로 통제된 성능 대조군으로 취급하지 않는다.
6. 9개 job 모두 `선언 수 = passed + skipped`, 시간 있는 성공 기록 수 = passed, worker 2, retry/failed/flaky 0을 대조했다. 성공 기록 1,297개와 skip 161개가 선언 1,458개에 맞는다.

### 2. 테스트 수보다 공통 작업의 실행 단가 차이가 크다

데스크톱 통과 수는 두 실행 모두 모바일보다 7개 적었다. 동명 시나리오를 연결한 worker 시간 합계는 다음과 같다.

| 표본  | 공통 시나리오 | desktop 합계 | mobile 합계 | desktop만 실행한 항목 |
| ----- | ------------- | ------------ | ----------- | --------------------- |
| 11-14 | 132개         | 약 522.3초   | 약 343.3초  | 10개, 약 51.7초       |
| 11-15 | 143개         | 약 577.6초   | 약 537.6초  | 10개, 약 60.4초       |

이는 공통 작업의 비용과 화면별 전용 작업을 함께 봐야 한다는 근거다. 특히 공통 작업의 차이가 179초에서 40초로 달라지므로 "데스크톱 픽셀이 많아 항상 일정 배수로 느리다"거나 특정 앱 회귀로 단정하지 않는다. 각 job은 별도 실행기다. CPU·메모리·서버 대기·스크린샷 시간을 구분할 기존 계측은 없어 그 인과관계는 미확정이다.

11-14 데스크톱의 테스트 보고 시간 합계는 약 574초다. worker 2개로 나누면 약 287초이고 브라우저 명령은 309초였다. 최신 실행도 약 638초 / 2 = 319초에 대해 명령은 342초였다. 이미 병렬 슬롯에 실제 테스트 시간이 많이 들어가 있어 단순히 `fullyParallel`을 켜거나 큰 대기 한 곳만 삭제하면 해결되는 상황은 아니다. 이 계산은 **CPU 사용률**이나 순수 계산 시간 측정이 아니다.

가장 긴 native font는 이전 두 실행에서도 약 25초였다. 그러나 그것 하나가 전체 5~6분을 설명하지는 않는다. 목차 UI 추가 전 실행에도 데스크톱 브라우저 명령은 이미 5분대였다.

responsive 설정은 별도 production 지정이 없으면 `dev:e2e`의 `next dev` 경로를 사용하며, 공용 계약·UI 패키지도 서버 시작 전에 빌드한다. 기존 콘솔은 기동·최초 route compile·요청·브라우저 계산 시간을 단계별로 분리하지 않는다. 소스에 개발 서버가 있다는 이유만으로 5분 전부가 컴파일 비용이라고 단정할 수 없다.

이 화면들은 동작·접근성·서버 응답·직접 접근을 서로 다르게 검증한다. 같은 URL을 사용한다는 이유만으로 중복 테스트라고 보거나 삭제할 수 없다. skeleton의 원본 HTML과 실제 hydrated 화면도 다른 검사 대상으로 보존해야 한다.

### 4. 불필요한 고정 sleep은 발견하지 못했다

현재 `e2e`에 `page.waitForTimeout`이나 `networkidle` 대기는 없다. `test.setTimeout(120000)`은 일부 다중 경로/프로필 검사의 **최대 허용 시간**이지 매번 120초 기다리라는 코드가 아니다. `article-shell-stability`의 20초 timer도 관찰용 interval을 정리하는 예약이며 그 시간을 직접 await하는 sleep이 아니다.

따라서 timeout을 줄여 빨라졌다고 하거나, 폰트·hydration·키보드·서버 pending 조건을 기다리지 않고 측정하는 방식은 개선안에서 제외한다.

### 5. 전체 CI의 임계 경로도 함께 봐야 한다

최신 CI는 6분 45초였다. 데스크톱 완료는 01:34:43 UTC, 모바일은 01:34:33 UTC로 10초 차이다. 다른 job이 그대로라는 가정에서 데스크톱만 극단적으로 줄여도 임계 경로는 모바일로 옮겨간다. **전체 CI가 절반으로 줄어든다는 결론은 낼 수 없다.** 이 10초는 현재 완료 시각의 차이이며 개선을 실행한 측정값은 아니다.

Playwright 공식 [CI 안내](https://playwright.dev/docs/ci#workers)는 안정성을 우선하면 worker 1개를 권장하며 더 넓은 병렬화에는 샤딩을 제시한다. [샤딩 안내](https://playwright.dev/docs/test-sharding)는 독립 job 분산과 fullyParallel 기반 개별 테스트 분배를 설명한다. 이번 프로젝트에는 fullyParallel이 이미 적용돼 있다. 최신 문서의 신규 API를 설치 버전 검증 없이 도입하지 않는다.

후속 실험의 수용 기준:

- 테스트 ID·언어·테마·폭·직접 URL/Link 구분·원격 fixture 계약과 assertion을 보존한다.
- timeout·retries·실패 처리·집계 gate·공개 증거 제한을 완화하지 않는다. 첫 시도 실패·재시도 비용을 따로 기록한다.
- 동일 SHA의 cold/warm 조건을 구분하고 최소 3회 반복한다. 최장 job뿐 아니라 전체 CI 시간·runner 사용량·비용·flake를 비교한다.
- 직접 접근을 확인하는 `page.goto`를 임의로 Link 이동으로 바꾸지 않는다. 실제 사용자 이동 검사는 기존 Link 계약을 유지한다.
- dev를 production으로 바꾸기만 하고 더 빨라졌다고 결론 내리지 않는다. 개발 경로·production/streaming 검사는 범위가 다르다.
- 원시 trace·리포트를 공개 artifact로 올리지 않는다. 이번처럼 집계와 한계만 정리하고 공개 전 별도 검수를 거친다.

최초 조사는 기존 CI 결과 9개와 소스 분석이다. Linux benchmark·CPU profile은 실행하지 않았으며, 분석 대상은 성공한 3개 커밋이므로 실패/flake의 전체 빈도를 추정하지 않는다. 후속 로컬 실험은 아래처럼 별도로 구분한다.

### 로컬 계측·범위 보존 후속

2026-11-15 KST, macOS·Node 24.22.1·pnpm 12.14.0·설치된 Chromium에서 실행했다. 별도 loopback 포트와 기존 `dev:e2e` 경로를 사용한다. 로컬 retry 0은 기존 설정 그대로이며 CI의 retry 2를 바꾸지 않았다. 실행기·CPU 제한·cache·백그라운드 부하가 Linux CI와 같지 않다. 초기 기준 반복 중에는 저장소 회귀 검사도 일부 겹쳐 통제된 overhead 실험으로 취급하지 않는다.

구현 범위:

- 고정 단계명으로 서버 HTML·이동·폰트·기하·snapshot 준비·프로필 시작/종료·캡처 시간을 계측한다. 기본은 꺼져 있고 사용자 실험 명령에서만 켠다. 계측을 끄면 기존 Promise를 그대로 반환한다.

`PRIVATE_RESULTS`와 `COUNTERS`는 위 재현 절차와 [runbook](../../runbooks/docs-e2e-performance.md)의 `mktemp` 준비를 따른다. 기존 표본은 덮어쓰지 않는다. 다음은 별도 스켈레톤 HTTP 실패 분리와 캐시 준비 지연의 재현 조건 조사다. 키보드 실패를 다시 focus 문제로 묶거나, 기존 timeout·retry·채택 gate를 낮추는 근거로 쓰지 않는다.
