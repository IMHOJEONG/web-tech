# Docs와 Vuln Radar의 초기 JavaScript·분석 스크립트 비용

## 대상과 조건

2026-11-25 KST. 저장소 기준은 PR #112를 병합한 `5dc0e252`이며, 직전 도식 치수 수정의 로컬 커밋은 `9630878d`다. 공개 서비스의 Docs 목록·폼 오류 복구 글, Vuln Radar Overview·Feed를 측정했다. [KAN-83](https://web-tech-service.atlassian.net/browse/KAN-83) · [P2 실행 계획](../../todo/modern-web-guidance.md#4-p2--초기-javascript와-외부-스크립트-비용-재평가)

Chromium의 390×850px(DPR 2)과 1280×850px(DPR 1), 네트워크 지연 80ms·다운로드 200,000B/s·CPU 4배에서 새 컨텍스트를 사용했다. 브라우저 캐시와 서비스 워커는 비활성화했다. 사이트와 브라우저가 요청한 스크립트를 읽고, 검증 방문에서 발생하는 POST와 분석 이벤트 전송은 차단했다. 정상 조건마다 두 번 실행했으며 Docs 모바일에는 대조군 네 번을 추가했다.

## 재현 방법

1. [Docs 목록](https://heap-forge.app/ko/docs), [일반 본문](https://heap-forge.app/ko/docs/ui-ux/form-error-recovery), [Vuln Radar Overview](https://vuln-radar-service.vercel.app/overview), [Vuln Radar Feed](https://vuln-radar-service.vercel.app/feed)를 새 컨텍스트에서 연다. Docs는 검색 버튼이 활성화될 때, Vuln Radar는 `main`과 Feed 내비게이션이 나타날 때의 시각을 기록한다. 이 시각에 1.6초를 더한 곳까지 초기 관측 구간으로 삼는다.
2. DevTools Protocol의 `Network.loadingFinished`로 성공한 JS 응답의 압축 전송 바이트를 집계한다. 이 값에는 프로토콜 헤더가 포함될 수 있다. `Performance.getMetrics`의 `ScriptDuration`은 구간 누적 실행 시간을, V8 CPU 프로파일은 로드된 파일별 샘플의 자기 실행 시간을 제공한다. `long-animation-frame`에서 50ms 이상 프레임과 `blockingDuration`을 수집한다. 세 수치는 각각 기록한다. [Chrome Performance 도구](https://developer.chrome.com/docs/devtools/performance/reference) · [CDP Performance](https://chromedevtools.github.io/devtools-protocol/tot/Performance/)
3. 모바일 Docs에서는 같은 문서를 정상 로드와 Vercel Analytics·Speed Insights 스크립트 두 개의 차단 대조군으로 번갈아 연다. Cloudflare 스크립트는 각 조건에서 관측한다. 스크립트 요청을 실제로 포착했고, 정상군에는 200 응답이 있으며 차단군에서는 두 응답이 없는지 각각 검사한다.
4. Docs는 초기 관측 후 검색 트리거를 키보드 Enter로 열고 입력 포커스까지의 시간, Escape 닫기와 트리거로의 포커스 복귀를 확인한다. 이 구간에 새로 관측한 JS 응답을 집계한다.

설치 SDK의 기본 경로와 공개 사이트가 실제 요청한 경로가 달랐다. 공개 요청의 스크립트 내용을 조회해 `window.va`와 `window.si`를 식별한 뒤 차단 대상을 바로잡았다. 기본 경로를 가정한 초기 실행은 대조 결과에서 제외했다. Cloudflare의 브라우저 요청은 저장소의 직접 선언 경로와 별도로 관측했다.

## 결과와 증거

아래는 정상군 두 번의 범위다. JS는 해당 앱의 성공한 초기 JS 응답의 전송량이며 kB는 1,000바이트다. `ScriptDuration`은 초기 구간의 누적 실행 시간이다. 긴 프레임 열의 값은 해당 조건의 최대 `blockingDuration`이다.

| 앱·화면             |         폭 | 초기 앱 JS kB | ScriptDuration ms | 긴 프레임 차단 최대 ms |
| ------------------- | ---------: | ------------: | ----------------: | ---------------------: |
| Docs 목록           |        390 |         434.3 |       2,117–2,130 |                     84 |
| Docs 목록           |       1280 |   434.4–438.0 |       1,876–2,913 |                     85 |
| Docs 본문           |        390 |   446.4–450.0 |       2,038–3,127 |                     98 |
| Docs 본문           |       1280 |         446.4 |       2,153–2,183 |                     81 |
| Vuln Radar Overview | 390 / 1280 |         148.2 |           227–239 |                    120 |
| Vuln Radar Feed     | 390 / 1280 |         148.2 |           213–223 |                     97 |

- **Docs 앱 실행:** 정상 8회에서 공통 React DOM 런타임이 포함된 파일의 자기 실행 표본이 각 실행에서 1.21~2.08초로 가장 많았다. 파일 응답에서 `react-dom`과 React의 오류 표식을 확인했다. 샘플링은 청크 단위이며 하이드레이션 안의 특정 컴포넌트 비용은 별도 계측이 필요하다.
- **분석 요청:** Vercel Analytics 2.7kB, Speed Insights 8.3kB, Cloudflare 10.5kB였다. Vercel 두 스크립트의 전송을 차단했을 때 검색 트리거 준비 시간은 모바일 목록의 두 번에서 각각 약 970ms·980ms 길어졌고, 일반 본문에서는 약 1,077ms 짧아진 경우와 27ms 길어진 경우가 있었다. 실행 표본에서 분석 파일의 자기 실행 시간은 각 스크립트 최대 약 2ms·6ms·16ms였다. 이 범위에서 로딩 순서를 바꿀 근거가 부족했다.
- **사용 경로:** Docs의 정상·차단 12회에서 키보드로 Drawer를 열고 입력으로 포커스가 이동한 뒤 Escape로 닫고 트리거로 돌아왔다. 최초 입력 포커스는 77~96ms였으며 이 구간의 새 JS 응답은 0개였다. React Scan·React Grab 요청은 공개 표본에서 관측되지 않았다.
- **Vuln Radar:** Overview와 Feed는 두 폭에서 모두 같은 Vite JS 파일 한 개를 받았다. 두 화면의 독립 번들을 다시 도입할 판단에는 초기 전송 절감과 화면 이동 비용을 함께 비교하는 대조가 필요하다. [이전 분리 실험](2026-11-22-vuln-radar-route-splitting.md)

관측값은 [정제 증거](../artifacts/2026-11-25-initial-js-cost.json)에 있다. 앱 스크립트와 SDK에 대한 제품 변경은 이번 진단 범위에서 발생하지 않았다.

### 후속 검증 — Docs 헤더의 하이드레이션

로컬 `9630878d`를 기준으로 격리 사본 두 개에서 합성 Docs 목록과 본문을 제공했다. Next 16.4.6의 `build --webpack --profile`을 사용했다. [앞선 Docs 측정](2026-11-25-docs-production-cwv.md#재현-방법)과 동일한 `.mts` 호환 처리를 격리 사본에서 적용했다. 이번 Chromium 측정의 폭·네트워크·CPU 조건은 위와 같고, 문서·폭·빌드마다 새 컨텍스트에서 세 번 반복했다. 기준을 먼저 측정하고 후보를 별도 배치에서 측정했다.

- 헤더, 본문, 하단 내비게이션, 하위 헤더 기능 등을 React `Profiler`로 감싸고, DOM에서 검색 트리거가 활성화된 뒤 1.2초까지 기록했다. `actualDuration`은 해당 경계가 커밋되기까지 렌더링한 시간이다. 서로 중첩되는 헤더와 하위 컴포넌트의 값을 함께 더하지 않는다. [React Profiler](https://react.dev/reference/react/Profiler)
- 탐색의 `responseStart`와 검색 트리거 `disabled` 해제는 같은 페이지 시계에서 수집했다. 초기 JS 평가 시간은 DevTools의 페이지 렌더러 메인 스레드 `EvaluateScript` 구간을 합집합으로 계산했다. CDP `ScriptDuration`에는 평가 외 JS 실행이 포함되며, JS 실행과 React 렌더링 수치를 그대로 더할 수 없다.
- 기준의 헤더 렌더링 중앙값은 32.2~36.2ms였다. 헤더 안에서는 모바일 메뉴가 22.1~24.3ms, 검색 Drawer가 4.8~5.9ms였다. 하단 내비게이션은 2.2~2.8ms였다. 여기서 모바일 메뉴는 헤더에서 여는 왼쪽 Drawer다.
- 후보는 모바일 메뉴의 트리거와 `SheetContent`를 유지하고, 닫혀 있는 패널의 JSX 생성과 번역 조회를 내부 컴포넌트로 옮겼다. 기존 포털이 패널을 마운트할 때 실행되는 방식이다. 모듈은 동일한 정적 import 경로를 사용했다.

기준 세 번의 중앙값이다. 서버 응답과 검색 활성화는 탐색 시작 기준 시각, 나머지 열은 소요 시간이다.

| 문서·폭   | 서버 응답 ms | JS 평가 ms | 누적 JS 실행 ms | React 헤더 ms | 검색 활성화 ms |
| --------- | -----------: | ---------: | --------------: | ------------: | -------------: |
| 목록 390  |           18 |        366 |           2,211 |          35.8 |          5,741 |
| 본문 390  |           31 |        342 |           1,804 |          32.2 |          5,070 |
| 목록 1280 |           19 |        338 |           2,225 |          36.2 |          5,741 |
| 본문 1280 |           25 |        340 |           1,825 |          34.6 |          5,089 |

후보 비교는 기준 → 후보 중앙값이다. 긴 프레임은 각 실행의 최대 차단 시간을 본다.

| 문서·폭   | 모바일 메뉴 렌더 ms | 헤더 전체 렌더 ms | 검색 활성화 ms | 긴 프레임 차단 ms |
| --------- | ------------------: | ----------------: | -------------: | ----------------: |
| 목록 390  |         23.9 → 23.0 |       35.8 → 36.3 |  5,741 → 5,764 |         142 → 147 |
| 본문 390  |         22.1 → 22.2 |       32.2 → 34.3 |  5,070 → 5,098 |         132 → 152 |
| 목록 1280 |         24.3 → 22.4 |       36.2 → 35.8 |  5,741 → 5,748 |         129 → 141 |
| 본문 1280 |         23.6 → 22.7 |       34.6 → 35.8 |  5,089 → 5,105 |         132 → 151 |

모바일 메뉴 렌더링은 세 조건에서 0.9~1.9ms 줄었다. 네 조건에서 공통으로 개선된 전체 지표는 없었다. 이 후보는 격리 빌드에서 검증하고 제품 적용을 보류했다.

- 기준과 후보의 24회에서 Enter로 Drawer 첫 열기, 입력 포커스, Escape 복귀를 확인했다. 첫 열기부터 입력 포커스는 기준 77~104ms, 후보 84~107ms였다.
- 각 빌드의 목록·본문과 두 폭을 교차한 8회에서 Tab·위아래 방향키의 결과 링크 이동과 Enter 전체 검색을 확인했다. Enter 이후 URL이 바뀌고 HTML의 검사용 표시가 남아 같은 문서 탐색을 확인했다.
- 모바일 메뉴의 두 빌드·두 문서 4조건에서 초기 이후의 새 JS 요청을 차단한 상태로 첫 열기를 확인했다. 이어서 Escape 복귀, 639→640px 전환에서 닫힘과 오버레이 제거, 메뉴 링크 탐색, Enter 전체 검색의 실제 합성 결과 표시를 확인했다.

[하이드레이션 정제 증거](../artifacts/2026-11-25-docs-hydration.json)에 집계의 원본 숫자와 기준·후보 파일 해시가 있다. 실험이 끝난 두 프로덕션 서버는 종료했다.

## 한계와 후속 작업

제어된 브라우저의 소수 공개 페이지 표본이다. 로드 시간에는 서로 다른 서버 응답 시간과 하이드레이션을 포함한다. CDN 캐시·프로파일러 관측 오버헤드의 영향을 받는다. 청크 이름으로 분류한 CPU 표본만으로 특정 React 컴포넌트의 병목을 확정할 수 없다. 필드 INP·분석 이벤트 실제 수신은 측정 범위 밖이다.

추가 개선 후보는 Docs 공통 셸의 초기 JS 실행을 더 작은 작업으로 나눠 계측한 결과로 고른다. 이번 프로파일 표본은 격리 Webpack 빌드·합성 내용·Chromium 결과이며, 운영 Turbopack 페이지의 절대 시간과 직접 대조하지 않는다.
