# Atlassian 결과 카드 초기화 시간 초과 진단

2026-11-21 기록 정리: 앱 버전·조회 소요 시간·45개 초기화 관측과 공개 댓글 게시 결과는 11-11 당시 기록이다. 오늘의 앱 버전·제공자 수정 여부를 재검증하지 않았고 새 진단·댓글·원시 자료 제출은 하지 않았다. 경고와 초기화 실패의 인과관계는 계속 미확정이다.

## 대상과 조건

- 검토일: 2026-11-11, Asia/Seoul. 로그 시각은 아래에서 UTC와 KST를 구분한다.
- 대상: Codex Desktop에서 Atlassian 검색 결과 카드를 여는 경로. 블로그/NAS 서비스의 요청이 아니다.
- 저장소 기준: `994bad1`. 애플리케이션 소스, 의존성, 자격 증명, 설치 앱은 변경하지 않았다.
- 환경: macOS 26.6.2, arm64. 현재 앱의 업데이트 검사 응답은 `26.1103.60933`, build `25894`, `prod`, `up_to_date`였다. 실패 시각의 같은 앱 로그에서도 `buildNumber=25894`를 확인했다. 별도 디스크 경로에서 읽은 `26.1027.51404` / `23880`은 재현 앱 버전으로 사용하지 않는다.
- 연결 플러그인 리소스에서 관측한 Atlassian 버전: `2.0.2`. 이 값은 서버/프런트엔드 번들의 빌드 식별자가 아니다.
- 자료: 사용자가 확인한 카드 실패, 같은 시각대의 로컬 앱 이벤트, 이 채팅에서 수행한 읽기 요청, 공개 npm 배포본의 정적 비교.
- 상태: 실패 단계 확인, 근본 원인 미확정. 2026-11-11 사용자 승인으로 [영문 재현 댓글](https://github.com/openai/codex/issues/60463#issuecomment-6785068760)을 게시하고 승인 본문과의 정확한 일치를 재조회했다. 원시 자료 제출과 저장소 커밋·푸시는 하지 않았다.

## 재현 방법

1. Atlassian에 연결된 Codex Desktop 채팅에서 접근 가능한 Jira 이슈를 JQL로 조회한다.
2. 필드는 제목과 상태, 결과 수는 3개로 제한한다. 도구 반환 여부와 소요 시간을 별도로 확인한다.
3. 연결 도구의 검색 결과 카드를 연다. 목록 표시 성공인지 시간 초과 화면인지 확인한다.
4. 한 번 재시도하고, 데이터 반환 성공과 카드 초기화 실패를 각각 기록한다. 이번 사용자 확인에서는 새 카드도 같은 시간 초과였다.
5. 로컬 앱 로그의 같은 초기화 시도에 속하는 프레임 로드와 오류를 내부적으로 대조한다. 세션/초기화 식별자는 대조에만 쓰고 문의 자료에는 넣지 않는다.

환경 확인에 사용한 명령은 다음과 같다. 별도 앱 업데이트나 재시작은 실행하지 않았다.

현재 앱의 버전은 읽기 전용 `check_app_update` 응답과 재현 로그의 빌드 번호를 대조했다. 아래 `plutil` 명령은 지정한 디스크 경로의 번들만 읽으므로, 그 결과를 실행 중 앱 버전으로 대신 사용하지 않았다.

```sh
sw_vers
uname -m
plutil -extract CFBundleShortVersionString raw /Applications/Codex.app/Contents/Info.plist
plutil -extract CFBundleVersion raw /Applications/Codex.app/Contents/Info.plist
```

로그는 로컬에서만 읽었다. 원시 로그, 화면 캡처, HAR, 응답 본문을 이 저장소에 복사하지 않았다.

### 초기화 단계 추가 대조

00:18 KST 재현의 동일한 초기화 식별자로 `Connected app sandbox`와 `Starting app widget`을 00:18:11.938에 확인했다. 그 뒤 프레임이 로드됐고, 00:18:12.126에 콘솔에 `[object Object]`가 기록됐다. 초기화가 시간 초과된 뒤 샌드박스가 제거됐다. 따라서 샌드박스에 연결하기 전의 실패는 아니지만, 내부 위젯 통신까지 성공했다는 뜻도 아니다.

같은 시각대 `mcpServer/resource/read` 응답은 506ms에 오류 코드 없이 라우팅됐으나, 해당 행에 같은 초기화 식별자가 없어 이 시도의 특정 리소스와 연결하지 않는다. 해당 로그 파일에서 `ui/initialize`, 초기화 완료 알림, 도구 결과 전달 알림의 직접 기록은 찾지 못했다. 메시지가 없었다는 증거가 아니라 현재 로그로 송수신 여부를 판정할 수 없다는 뜻이다. `[object Object]`의 원래 값도 알 수 없어 JS 예외 또는 네트워크 실패로 분류하지 않는다.

### 버전 중복 경고 정적 추적

`@atlaskit/feature-gate-js-client`의 `5.8.0`, `6.0.0` 공개 배포본을 조회했다. CDN 결과만 신뢰하지 않고 공식 npm registry의 tarball도 메모리에서 압축 해제하여 metadata의 SHA-512 integrity와 대조했다. 두 버전 모두 일치했다. 패키지 설치, lifecycle script 실행, 내려받은 코드 실행은 하지 않았다.

| 비교 대상                         | 두 tarball의 결과                                                                      |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| `dist/esm/client/FeatureGates.js` | 각각 8,413 bytes, SHA-256 동일                                                         |
| `dist/esm/client/Client.js`       | 각각 63,710 bytes, SHA-256 동일                                                        |
| 경고 분기                         | 기존 전역 클라이언트를 재사용하고 `console.warn` 호출. 해당 분기에 명시적 `throw` 없음 |
| `dist/esm/client/version.js`      | 두 배포본 모두 `5.8.0` 문자열. package metadata는 각각 `5.8.0`, `6.0.0`                |

정적 비교 SHA-256:

- `FeatureGates.js`: `e3ffee1b185975d6145d43d6bff9c6a6cb9d09a28f0245ce405ebf12d3d73d9d`
- `Client.js`: `da097ee0de2f3b1eafa54c40aae6fee29f40ceba704470ecf2a5fa0f6da6c6b6`

**결론:** 경고 자체가 예외를 던져 카드 실행을 즉시 중단시킨다는 설명은 이 공개 코드에서 지지되지 않는다. 그러나 전역 singleton 재사용, 다른 의존성, 실제 제공자 번들의 빌드 차이까지 안전하다고 증명한 것은 아니다. 공개 패키지의 버전 문자열과 실제 경고의 `6.0.0`이 바로 대응하지도 않으므로, 공개 배포본을 실제 카드 번들과 동일시하면 안 된다.

로그에서 경고와 실패가 함께 나타났지만, 경고를 제거한 같은 카드의 통제된 A/B 검사는 수행하지 못했다. 초기화가 취소되거나 다른 오류로 끝난 기록은 정상 대조군으로 계산하지 않았다. 따라서 인과관계는 미확정이다.

추가로 시작 시각을 UTC `2026-11-09T00:29:56.197Z`부터 `2026-11-10T22:56:44.205Z`까지 포함하는 고정 구간으로 정하고, Atlassian 카드 시작과 프레임 로드가 모두 기록된 서로 다른 초기화 식별자 45개를 대조했다. KST로 11월 9일 09:29부터 11월 11일 07:56까지다. 45개 모두 중복 경고가 있었고 43개는 시간 초과를 기록했다. 나머지 2개는 프레임 로드 후 정확히 2.133초와 3.497초에 샌드박스가 제거됐으며 정상 표시를 확인할 수 없다. 재시도가 포함된 한 환경의 관찰이므로 사용자별 장애율이나 경고의 인과관계로 해석하지 않는다.

### 추가 내용 재검증

같은 날 원본 로그를 다시 읽고 고정 구간의 집계와 시간 차이에 assertion을 적용했다. 45개/43개/경고 45개, 조기 제거 2.133초/3.497초, 실패 간격 5.126초/5.002초가 모두 일치했다. 같은 초기화 식별자의 샌드박스 연결 시각과 콘솔 객체 기록 시각도 일치했다. 앞선 도구 응답의 별도 저장 메타데이터에서 1,313ms, 결과 3개, 오류 없음도 재확인했다. 새 시도의 성공률이나 네트워크 wire trace를 측정한 검사는 아니다.

문의 요약에는 현재 앱 버전과 빌드 근거를 사용한다. 내부 초기 기록에만 남아 있던 이전 디스크 번들 값은 별도 정정 기록으로 구분했다. 외부 보고나 웹 대조의 성공으로 바꿔 적지 않았다.

### 유사 공개 보고

OpenAI 저장소의 [Codex 이슈 #60463](https://github.com/openai/codex/issues/60463)에 Windows에서 같은 초기화 오류와 데이터 읽기 성공을 분리한 사용자 보고가 있다. macOS의 Confluence 카드 댓글은 이 환경과 같은 앱 버전 `26.1103.60933` / build `25894`를 보고했고, 별도의 macOS Jira 카드 재현 댓글도 있다. 같은 빌드에서 다른 카드 유형까지 보고됐다는 단서이며, 동일 원인이나 수정 여부가 확인된 것은 아니다.

[OpenAI 문제 해결 안내](https://developers.openai.com/plugins/deploy/troubleshooting)는 서버, 컴포넌트, 클라이언트를 분리하고 카드 실패 시 CSP와 번들 로딩을 확인하도록 안내한다. [UI 통신 문서](https://developers.openai.com/plugins/build/chatgpt-ui)는 도구 결과와 UI 초기화 통신을 별도 단계로 설명한다. 이 일반 문서가 이번 제공자 구현의 결함을 확정해 주지는 않는다.

## 제공자 문의용 요약

아래는 한국어 진단 요약이다. 사용자가 한국어 내용을 검토한 뒤 승인한 영문 버전은 [공개 댓글](https://github.com/openai/codex/issues/60463#issuecomment-6785068760)로 게시했다. OS/검증 환경 표, 정정한 앱 버전, 경고 인과관계 미확정 문구를 포함했으며 첨부 없이 본문만 전송했다.

**제목:** Codex Desktop의 Atlassian 카드가 데이터 조회 성공 후 위젯 초기화 시간 초과로 표시되지 않음

- 환경: macOS 26.6.2 / arm64. 현재 Codex 앱의 업데이트 검사는 26.1103.60933, build 25894, prod, up_to_date를 반환했다. 재현 시각의 로컬 앱 로그에서도 build 25894를 확인했다.
- 재현: Jira 검색을 제목/상태 필드와 결과 3개로 제한하면 도구는 약 1.31초에 데이터를 반환한다. 이후 검색 결과 카드를 열면 시간 초과 화면이 표시된다. 새 카드에서도 사용자가 재현을 확인했다.
- 관측: UTC 2026-11-10 15:18:11.969에 프레임 로드, 15:18:17.095에 `MCP app initialization timed out`과 `stage=widget`. 별도 시도에서도 약 5초 후 동일 오류다.
- 인접 경고: FeatureGateClients의 기존 버전 6.0.0과 로딩 버전 5.8.0 중복. 공개 패키지의 해당 경고 분기는 throw 없이 기존 전역 클라이언트를 재사용한다. 실제 제공자 번들의 원인이라는 증거는 아직 없다.
- 영향: 카드 이용은 불가능하지만 반환된 데이터를 일반 텍스트로 확인하는 경로는 동작한다. 전체 Jira 장애나 인증 만료로 확정하지 않았다.
- 관련 공개 보고: <https://github.com/openai/codex/issues/60463>. 유사 증상 참고이며 동일 원인 확인은 요청한다.
- 요청: 아래 초기화 통신과 실제 번들 계측을 확인해 달라. 인증 초기화나 캐시 삭제부터 수행해야 한다는 근거는 아직 없다.

제공자에게 요청할 추가 확인:

1. 해당 시도의 `ui/initialize` 요청·응답, 완료 알림 중 어느 단계가 누락/지연되는가? 현재 로컬 로그만으로는 요청 전송 여부도 확정할 수 없다.
2. 도구 결과가 해당 iframe에 전달됐는가? 초기화 제한 시간과 데이터 읽기 제한 시간을 구분할 수 있는가?
3. 전체 JS 오류와 실패한 네트워크 요청, CSP/origin 거부가 있는가? 로컬 로그의 `[object Object]` 기록만으로 숨은 오류의 내용을 알 수 없다.
4. 실제 카드 번들의 FeatureGate singleton, 의존성, 버전 주입 경로는 무엇인가? 경고 제거 전후 같은 빌드·계정·입력의 A/B를 제공자 환경에서 비교할 수 있는가?
5. 공개 이슈 #60463과 같은 결함인가? 수정 버전이나 별도의 진단 절차가 있는가?

## 한계와 후속 작업

- 확정한 것은 카드 초기화 단계의 실패다. UI 프로토콜 호환, 추가 네트워크 지연, 번들 오류 중 하나를 근본 원인으로 선정하지 않는다.
- 실제 카드 번들/네트워크 trace, 정상 카드 대조군, 다른 호스트에서의 같은 계정 검사, 앱 재시작·업데이트 후 검사는 미실행이다.
- 호스트 대조를 할 경우 같은 계정·연결 앱·JQL·결과 수를 유지하고, 일반 웹 브라우저의 채팅 앱에서도 같은 유형의 결과 카드를 열 수 있을 때만 비교한다. Jira 사이트에서 검색만 성공하거나 웹에서 카드가 제공되지 않는 경우는 카드 정상 대조군이 아니다. 웹에서만 성공하면 데스크톱 경로를 우선 조사하되 배포 리소스와 호스트 버전 차이도 확인한다. 양쪽 실패라면 공통 번들/호스트 통신 경로도 후보에 둔다.
- 앱 강제 패치, CSP 완화, 전역 객체 덮어쓰기, 경고 숨기기, 토큰 재발급, 연결 해제는 하지 않았다.
- 원시 HAR/로그는 인증·개인 정보가 포함될 수 있으므로 그대로 첨부하지 않는다. 제공자가 요청하면 별도 승인과 제거 검사를 거쳐 최소 항목만 전달한다.
- 테넌트 URL, 이슈 키/본문, 계정/메일, conversation/session/init 식별자, 로컬 사용자 경로, 쿠키, 토큰, 인증 헤더, 페이지 토큰은 문의 자료에서 제외했다.
- 사용자 승인 범위의 내부 추적 기록은 [작업 기록](../../worklog/2026-11/2026-11-11-atlassian-widget-timeout.md)에서 확인한다. 공개 댓글 게시와 원시 자료 제출은 구별하며, 원시 자료나 별도의 비공개 지원 문의는 보내지 않았다.
- 구조·공개 계약 변경이 없는 독립 진단이므로 새 ADR은 만들지 않는다.
