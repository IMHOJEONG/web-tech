# 서비스 복구와 배포 안전 정책

## 상태와 범위

- 상태: 제안
- 대상: docs, docs-backend, vuln-radar, vuln-radar-backend와 PostgreSQL
- 최종 검토: 2026-09-30

저장소의 기존 롤백 절차를 확장한 운영 기준이다. 아래 수치는 합의·리허설 전 초안이며 현재 달성하는 SLA가 아니다. NAS 백업 스케줄, DB 제공자의 복제·PITR 설정, Vercel Dashboard 설정은 확인하지 않았다.

## 배경

프론트 롤백 안내와 NAS 이미지 교체 절차는 있지만 복구 목표, 데이터 보관, 복구 성공 판정이 부족하다. docs-backend는 Markdown 볼륨을 사용하고 vuln-radar-backend는 PostgreSQL을 사용하므로 같은 복구 방식을 적용할 수 없다.

## 결정

### 복구 목표 초안

RTO는 장애 발생부터 주요 사용자 동작 복구까지의 목표 시간이다. RPO는 복구 시 허용할 데이터 손실 시간이며 마지막으로 복원 가능한 백업 시점으로 측정한다. 장애 감지 지연도 별도로 기록한다.

| 대상                            | RTO 초안 | RPO 초안  | 복구 성공 조건                                     |
| ------------------------------- | -------- | --------- | -------------------------------------------------- |
| docs·vuln-radar 프론트 코드     | 60분     | 해당 없음 | 이전 검증 배포로 이동 후 주요 route·검색·상세 정상 |
| NAS 원격 문서 API·콘텐츠·이미지 | 60분     | 24시간    | 인증된 목록·상세 및 대표 이미지 응답과 콘텐츠 일치 |
| vuln-radar PostgreSQL           | 4시간    | 24시간    | 스키마·관심 목록·연관 데이터·API 읽기/쓰기 정상    |

프론트 코드의 RPO 해당 없음은 외부 데이터 손실이 없다는 의미가 아니다. 블로그 로컬 fallback이 보이더라도 원격 콘텐츠 장애는 계속 기록한다. 게시 직전 백업과 매일 성공한 백업을 모두 확보해야 콘텐츠 RPO 초안을 평가할 수 있다. 원격 콘텐츠가 바뀐 뒤 백업이 없으면 24시간 목표를 보장하지 않는다.

### 배포와 롤백 기준

- 담당은 현재 저장소 운영자다. 배포 실행자·복구 실행자와 승인 시각을 기록하며 담당 변경 시 이 문서를 갱신한다.
- 배포 전에 커밋 SHA, 이미지 digest 또는 deployment ID, 이전 검증 버전, 콘텐츠 계약·DB 스키마 호환성, 백업 식별자를 기록한다.
- 새 배포 직후 주요 route 5xx, 본문·검색 불능, 인증 우회, 데이터 오염이 재현되면 배포 확대를 중단한다. 일반 장애는 5분 내 원인 범위를 판단하고 이전 버전 호환성이 확인되면 수동 롤백한다.
- 인증 우회·정보 노출·데이터 손상은 5분을 기다리지 않는다. 쓰기/노출 경로를 먼저 격리하고 비밀값 교체 필요성을 판단한다.
- 이미지나 프론트 롤백은 콘텐츠·환경변수·토큰·DB를 되돌리지 않는다. 원인이 데이터라면 코드 롤백만 반복하지 않는다.
- DB 변경은 expand/contract를 우선한다. 새 필드 추가와 소비 코드 전환을 먼저 하고, 제거·제약 강화는 이전 버전 사용 종료 후 별도 배포한다. 파괴적 변경 이후 호환성이 없으면 자동 downgrade하지 않고 격리 복구 또는 forward fix를 선택한다.
- 회복 판정 후 15분 동안 주요 동작과 오류 증가를 관찰한다. 세 번의 단발 probe 성공만으로 장애 종료를 확정하지 않는다.

### 백업과 보관

- NAS는 Markdown과 이미지 원본을 같은 게시 버전으로 백업한다. 게시·대량 수정 전과 하루 한 번을 초안 주기로 삼는다.
- PostgreSQL은 하루 한 번 논리 백업을 초안으로 삼는다. dump 외에 확장, role/grant, 스키마 버전도 복구 가능한지 확인한다. 관리형 서비스에서 불가능한 항목은 제한으로 기록한다.
- 보관 초안은 일별 14개·주별 8개·월별 6개다. 이미지 복구 후보도 최근 검증 버전 최소 5개를 보존한다. 자동 삭제는 복구 가능한 최신 백업 확인 후에만 도입한다.
- 백업은 운영 볼륨과 다른 장애 도메인에도 암호화해 보관한다. 같은 NAS의 다른 폴더와 RAID만으로 재해 복구를 충족했다고 보지 않는다.
- 토큰은 콘텐츠 백업과 분리하고 접근 권한·암호화 키 복구 방법을 별도 관리한다. DB dump, NAS archive, 인증정보는 Git이나 CI artifact에 올리지 않는다.
- 백업 실패 또는 마지막 성공 백업이 24시간을 초과하면 운영자에게 알린다. 알림 경로와 스케줄은 아직 미구현이다.

### 리허설과 고가용성의 경계

첫 운영 적용 전, 이후 분기마다 및 배포·스키마·백업 방식 변경 후 격리 환경에서 복구한다. 명령 종료 코드 외에 데이터와 사용자 동작을 검사한다. 실제 RTO/RPO, 누락 데이터, 장애 감지·판단·복원 시간을 검증 보고서에 남긴다.

현재 NAS Compose는 단일 컨테이너 교체다. restart와 healthcheck는 롤링 배포·자동 롤백을 의미하지 않는다. 무중단 업데이트는 병렬 인스턴스, readiness 기반 트래픽 전환, 진행 중 요청 종료, 이전 버전 호환성과 실패 복귀 검사를 갖춘 뒤 별도 결정한다.

DB 복제는 백업의 대체가 아니다. DB 이중화는 제공자의 장애 전환, 데이터 손실 한계, 복제 지연과 쓰기 대상 전환을 실제 검증한 뒤 적용 상태로 바꾼다. 단일 connection URL만으로 이중화 여부를 판단하지 않는다.

## 대안과 영향

바로 롤링 배포·DB 복제를 도입하면 가용성은 개선될 수 있지만 NAS 메모리, 트래픽 전환과 데이터 일관성의 운영 부담이 늘어난다. 우선 백업 복원과 수동 롤백을 검증한다. 측정된 복구 시간이 목표를 넘거나 중단 비용이 증가하면 PITR·DB 장애 전환·단계적 배포를 재검토한다.
