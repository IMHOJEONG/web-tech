# ADR-0020: 원격 검색 목록의 비절단 byte budget

## 상태와 범위

- 상태: 적용 중
- 대상: docs-content-contract, docs-backend `GET /api/posts`, docs 원격 목록 소비자
- 결정일: 2026-10-26
- 최종 검토: 2026-10-26
- 로컬 구현·검증 범위이며 원격 CI·NAS/Vercel 배포·실제 corpus 용량은 미검증이다.

## 배경

[ADR-0019](adr-0019-remote-body-search.md)의 검색 텍스트가 목록 크기를 늘린다. 요청 deadline은 유지하지만 빠르게 도착하는 큰 응답의 메모리·파싱 비용을 제한하지 못한다. 압축 전송량이 작아도 압축 해제한 본문은 클 수 있다. 설치된 Next의 기본 fetch 캐시 구현에도 직렬화 항목 크기 제한이 있어 무제한 목록을 전제하지 않는다.

## 결정

공유 상수로 JSON의 압축 전 UTF-8 크기를 경고512KiB·상한1MiB로 정한다. 정확히512KiB는 정상, 이를 초과하고1MiB 이하이면 전체 목록을 유지하며 경고한다. 1MiB 초과는 목록 전체 실패다. 개인 블로그의 초기 보호 기준이며 성능 SLO·특정 NAS 용량·Next 캐시 적중을 보장하는 수치가 아니다. 상한 변경은 생산자/소비자·회귀·동일 corpus 재측정을 함께 검토한다.

백엔드는 canonical 스키마 검증 뒤 전체 payload의 JSON UTF-8 바이트를 계산한다. 초과하면503으로 거절하며 문서·본문·인증정보 없이 event·bytes·limitBytes·count만 기록한다. 요청 자체가 큰 것이 아니므로413을 사용하지 않는다. 인증·private/no-store·Vary 규칙은 유지한다. 경고 초과부터 별도 검색 인덱스·페이지 단위 목록을 재검토하고 단순 상한 인상으로 대응하지 않는다.

프론트는 목록 요청에만 같은 상한을 넘겨 JSON.parse 이전에 누적 스트림 바이트를 검사한다. 신뢰할 수 있는 identity Content-Length가 이미 크면 읽기 전에 거절하고, 누락·잘못된 값·작게 기재한 값은 실제 읽기로 검사한다. 압축 응답의 Content-Length는 전송 크기일 수 있어 사전 비교에 쓰지 않으며 압축 해제 후 전달된 청크가 기준이다. 초과 시 `too-large` 안전 오류·abort/cancel을 사용하고 기존 전체 deadline·retry0을 유지한다. 로그에 Request·헤더·본문을 붙이지 않는다.

원격 실패의 기존 로컬 fallback을 사용하며 부분 목록·metadata-only 성공으로 위장하지 않는다. 원격 전용 글은 일시적으로 목록/검색에 없을 수 있고, 목록을 사용하는 원격 상세도 로컬 사본이 없으면 오류가 될 수 있다. 이미 열린 화면·캐시의 자동 갱신은 기존 별도 정책이다.

## 대안과 영향

- 본문/목록 절단: 비용은 줄지만 뒤쪽 키워드를 놓치거나 일부 문서만 검색돼 제외한다.
- 초과 시 metadata-only: HTTP 성공과 실제 본문 검색 범위가 달라져 제외한다.
- 압축 크기·문서 개수 제한: UTF-8 본문 길이·압축률 차이를 반영하지 못해 단독 기준으로 쓰지 않는다.
- 무제한 허용·시간 제한만 유지: 큰 응답의 할당·파싱 비용을 방어하지 못한다.
- 별도 검색 endpoint/엔진·페이지 단위 동기화: 규모 확장에 유리하지만 새 캐시·게시 계약이 필요하므로 경고 이후의 후속 과제다.

이번 제한은 백엔드의 모든 원문 읽기/Markdown 파싱을 선제 제한하거나 메모리 OOM을 방지하는 완전한 방어가 아니다. 프론트도 이미 도착한 단일 청크의 할당이나 Next 내부 fetch/cache buffering을 되돌릴 수 없다. 상세 HTML 본문·공개 `/api/search` 결과의 별도 상한·동시 부하·실제 NAS 파일 크기 제한은 이번 범위 밖이다. 큰 파일·많은 짧은 문서로 구성한 경계와 실제 운영 corpus는 별도로 확인한다.
