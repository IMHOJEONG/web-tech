# ADR-0016: 수집 실행 관측과 데이터 기준일 분리

## 상태와 범위

- 상태: 적용 중
- 대상: vuln-radar frontend와 backend의 로컬 작업 트리. 운영 배포 미검증.
- 결정일: 2026-10-22
- 최종 검토: 2026-10-22
- 추적: [KAN-26](https://web-tech-service.atlassian.net/browse/KAN-26)

## 배경

화면은 60초마다 조회하지만 서버의 실제 수집은 별도 scheduler 설정을 따른다. 기존 `LATEST INGEST`는 DB 수정·원본 수정·KEV 등록·EPSS 관측 시각 중 하나를 선택하고 없으면 상태 조회 시각을 사용했다. 어느 것도 전체 수집이 성공했다는 실행 증거는 아니다. `REAL-TIME TELEMETRY` 역시 pull 방식과 맞지 않는다.

현재 DB에는 수집 실행 이력 테이블이 없다. 운영 DB에 migration을 적용하지 않는 범위에서 관측한 사실과 모르는 사실부터 구분한다.

## 결정

`GET /api/ingest/status`에 선택적으로 소비할 `observation`을 추가한다. 서버는 현재 프로세스의 실행 시작·종료·마지막 전체 성공과 소스별 조회 결과·마지막 조회 성공·실패·연속 실패 횟수를 기록한다. `scope: process`와 `observedSince`를 함께 제공하며 재시작하면 미확인으로 초기화한다. 원문 에러·인증값은 새 관측 payload에 포함하지 않는다.

- 전체 성공은 수집 함수의 DB 반영까지 완료됐을 때만 갱신한다. 일부 소스 조회 실패는 `partial`, primary 전부 실패·DB 반영 실패 등은 `failed`다. 이전 전체 성공 시각은 유지한다.
- 소스 조회 성공은 DB 반영 성공과 다르다. 변경0건도 실제 조회가 성공했으면 성공이며, 조회할 CVE가 없어 EPSS를 호출하지 않으면 `skipped`다.
- 실행 시작 전 같은 프로세스의 진행 중 실행을 확인해 수동·scheduler 중복은409로 거절한다. 이것은 분산 락이 아니다.
- frontend는 화면 조회 주기를 공통 상수에서 읽고 자동 수집 주기는 API scheduler 설정에서 읽는다. 자동 수집 비활성화와 설정 미제공을 구분한다.
- 구버전·재시작 직후의 이력은 미확인이다. `checkedAt`·DB 수정·원본 날짜를 성공 시각으로 대입하지 않는다.
- 실행 결과가 완료이고 자동 수집이 켜졌으며 마지막 전체 성공 후 설정 주기의 두 배를 넘었을 때만 확인 권장으로 표시한다. 지연 확인을 위한 UI 기준이지 장애 판정이나 수집 실행 SLA가 아니다. 진행 중·명시적 실패 결과를 나이로 덮지 않는다.
- NVD 원본 수정 시각, KEV 최신 등록일, EPSS 관측일을 소스 조회 성공 시각과 별도로 표시한다. KEV·EPSS는 UTC 원본 날짜를 유지하고 실행 시각은 기기 시간대로 표시한다.

상태 패널·API schema·순수 변환·실행 관측을 역할별로 나눈다. 전체 API 부분 장애 대응은 다음4번 과제로 남겨 기존 화면 오류 정책을 이번 변경으로 바꾸지 않는다.

## 대안과 영향

DB 수정 시각 추정은 추가 저장소가 필요 없지만 실제 실행 결과를 증명하지 못하므로 폐기한다. 프로세스 관측은 DB migration 없이 관측 사실을 전달할 수 있으나 재시작·다중 replica의 공통 이력을 제공하지 못한다. 이를 숨기지 않는1차 개선이다.

DB 영속 이력은 장기적으로 적합하지만 migration·보관 기간·실패 시 이력 기록·동시 실행의 공유 제어를 함께 설계해야 한다. replica 확대나 재시작을 넘는 운영 추적이 필요하면 영속 저장과 분산 실행 제어로 재검토한다. 현재 구현을 운영 이력 완성이나 장애 알림 시스템으로 간주하지 않는다.

frontend의 새 필드는 optional이므로 backend 선배포가 가능하고 구버전은 미확인으로 남는다. 기존 route와 집계 필드는 유지한다. 수동 sync의 새409는 같은 프로세스 중복 실행만 막으며 기존 scheduler 단독 플래그와 운영 인증을 제거하지 않는다.
