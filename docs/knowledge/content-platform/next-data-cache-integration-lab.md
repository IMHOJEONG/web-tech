# Next.js Data Cache 통합 테스트 실험 노트

## 목적

캐시를 설정했다는 사실과 실제로 캐시가 사용된다는 사실은 다르다.
이 문서는 `apps/docs`에서 원격 문서 캐시를 어떻게 검증했는지 설명하고,
나중에 같은 실험을 재현하거나 장애·동시성 실험으로 확장하기 위한 기록이다.

현재 운영 기준은 원격 목록/본문의 300초 TTL과 인증된 재검증 웹훅이다.
여기서는 기존 정책의 작동을 확인한다. 웹훅 성공 응답은 캐시 만료 처리를
뜻하며 NAS 조회 성공이나 사용자가 보는 화면의 변경까지 보장하지 않는다.

## 캐시 계층과 실험 범위

| 계층                            | 보관하는 결과          | 이번 실험                            |
| ------------------------------- | ---------------------- | ------------------------------------ |
| Next Data Cache                 | 원격 API 응답          | 원본 요청 횟수와 V1/V2 응답으로 검증 |
| Full Route Cache                | 정적 HTML/RSC 결과     | 동적 검증 경로에서 영향 배제         |
| 브라우저 Router Cache           | 화면 이동용 RSC 데이터 | 별도 브라우저 실험 필요              |
| 브라우저/Cloudflare 이미지 캐시 | 이미지 응답            | 별도 이미지 실험 필요                |

페이지를 반복해서 열었을 때 원본 호출이 없다는 관찰만으로 Data Cache를
증명할 수는 없다. 완성된 페이지 자체가 캐시되었을 수도 있기 때문이다.
이번에는 임시 Route Handler가 `connection()` 이후 실제 조회 함수를 실행한다.
렌더링 결과의 정적 캐시를 피하면서 데이터 캐시는 사용할 수 있게 한다.

React `cache()`를 통한 렌더 요청 내 중복 제거도 여러 HTTP 요청 사이에서
유지되는 Data Cache와 구분해야 한다. 이번 실험은 별도 HTTP 요청을 반복한다.

## 실험 구성

```text
테스트 실행기
  -> 현재 apps/docs를 임시 폴더로 복사
  -> next build --webpack
  -> next start (127.0.0.1, 임시 포트)
       -> 임시 /api/cache-probe
       -> 실제 content-api.ts / ky
       -> Next Data Cache
       -> 로컬 가짜 콘텐츠 API
            /api/posts                 : 목록 요청 카운터
            /posts/feed/cache-probe    : 본문 요청 카운터
```

가짜 API는 초기 V1 제목과 HTML 본문을 반환한다. 실행기가 원본을 V2로
바꾸어 NAS 파일 수정 상황을 재현한다. 응답에는 `private, no-store`를 붙이며,
그 응답을 재사용하는 Next 서버 측 정책은 실제 앱의 `next` 옵션으로 검증한다.

검증용 경로는 임시 앱에만 만들어진다. 일반 배포 앱에는 추가되지 않는다.
마지막에는 실제 `/docs/feed/cache-probe` 상세 라우트도 요청한다.
HTML에 V2 본문이 있는지 확인하며 시각적 UI 검사는 수행하지 않는다.

## 준비와 실행

Node.js 24와 설치된 워크스페이스 의존성이 필요하다.
저장소 루트에서 다음을 실행한다.

```bash
pnpm --filter @web-tech/docs-content-contract build
pnpm --filter @web-tech/ui build
pnpm --filter docs test:cache:prod
```

실제 `.env`, `.next`는 복사하지 않는다. 임시 인증값과 로컬 URL을 사용하므로
실제 NAS 접속 및 Vercel 캐시 만료는 발생하지 않는다.
의존성과 공용 패키지는 기존 설치를 참조하므로 실험 중 해당 빌드를 변경하지 않는다.
테스트가 실행한 서버와 임시 폴더는 종료 시 정리된다.

## 단계별 가설과 관찰

| 단계                     | 기대 결과                         | 목록/본문 누적 요청 |
| ------------------------ | --------------------------------- | ------------------- |
| 빌드 이후 초기 캐시 만료 | 빌드 때 만들어진 캐시의 영향 제거 | 시작 기준점 기록    |
| 첫 조회                  | V1 제목과 V1 본문, 원본 호출 발생 | 최초 기록에서 증가  |
| 두 번째 조회             | V1 재사용, 원본 호출 없음         | 유지                |
| 원본을 V2로 변경         | 캐시 내용은 자동으로 바뀌지 않음  | 유지                |
| 인증 누락/불일치 웹훅    | 401, 이후 조회도 V1               | 유지                |
| 정상 웹훅                | 200, 선제 원본 요청 없음          | 유지                |
| 다음 조회                | V2 제목과 V2 본문                 | 양쪽 모두 증가      |
| 추가 조회                | V2 캐시 재사용                    | 유지                |
| 실제 상세 라우트         | 200, HTML에 V2 본문 포함          | 관찰값 출력         |

2026-09-12 로컬 실행에서 최초 조회 후 목록/본문 카운터는 각각 1이었다.
반복 조회와 잘못된 인증 이후에도 각각 1을 유지했고,
정상 웹훅 이후 최신 조회와 상세 렌더링 확인 시 각각 2였다.
이는 해당 코드와 로컬 프로덕션 빌드에서 ky의 캐시 옵션 전달이 동작했다는 증거다.
모든 환경에서 반드시 1회만 호출된다는 보장은 아니므로 테스트는 기준점 대비
증가와 유지 여부를 판정한다.

## TTL과 즉시 만료의 차이

이번 테스트에서는 TTL을 3600초로 설정해 자연 만료가 웹훅 검증에 섞이지 않게 한다.
운영 기본값인 300초를 변경하는 것은 아니다.

시간 기반 재검증은 스케줄러가 아니다. 만료 이후 요청에 따라 갱신되며,
오래된 응답을 먼저 제공하고 백그라운드 갱신할 수 있다.
따라서 300초 이내 최신 반영을 보장한다고 해석하면 안 된다.

`revalidateTag(tag, { expire: 0 })`는 다음 조회를 캐시 미스로 처리하도록
즉시 만료시킨다. 호출 시점에 모든 원격 데이터를 다운로드하지 않는다.
갱신 직후 첫 조회의 지연과 원본 장애 처리를 함께 고려해야 한다.

## 실패했을 때 조사 순서

| 실패 지점                    | 우선 확인할 내용                                      |
| ---------------------------- | ----------------------------------------------------- |
| 빌드 실패                    | Node/의존성/공용 패키지 빌드, 출력된 최근 빌드 로그   |
| 첫 조회 실패                 | 가짜 API 계약, 경로 정규화, 인증, 실제 조회 함수 오류 |
| 반복 조회에서 원본 호출 증가 | next 옵션 전달, fetch 캐시 정책, 요청별 URL/헤더 변화 |
| 정상 웹훅 후 V1 유지         | 태그 연결, 웹훅 호출 대상, 목록과 본문 양쪽 설정      |
| 캐시는 V2지만 상세 HTML 실패 | canonical redirect, 본문 렌더링, 응답 정규화          |

테스트 실패는 캐시 라이브러리를 교체할 근거가 아니라 실패한 계층을 좁히는 출발점이다.
HTTP 200이어도 오류 화면일 수 있으므로 응답 내용도 함께 검사한다.

## 추후 실험 체크리스트

아래 항목은 아직 구현하거나 검증하지 않은 확장 후보다.
한 번에 하나의 조건을 바꾸고, 예상 결과와 관찰 결과를 따로 기록한다.

- [ ] TTL 만료: 짧은 TTL로 V1을 캐시하고 V2로 변경한 뒤, 만료 전/후 응답과 백그라운드 갱신 횟수를 관찰한다. 고정 지연만 기다리지 말고 제한 시간 내 상태를 확인한다.
- [ ] 원본 장애: 500, timeout, 잘못된 HTML을 각각 반환해 로컬 대체/오류 화면과 복구 후 결과를 확인한다. 기존 캐시가 항상 유지된다고 가정하지 않는다.
- [ ] 동시 조회: 캐시 만료 직후 여러 요청을 보내 원본 호출 수와 응답 시간을 측정한다. 요청 병합을 측정 전 보장으로 간주하지 않는다.
- [ ] 태그 세분화: 글 A/B를 준비해 A 수정 시 목록과 A만 갱신되고 B는 재사용되는지 확인한다.
- [ ] 반복 웹훅: 요청 제한 구현 후 정상 발행은 허용하고 초과 요청은 429인지 확인한다.
- [ ] 브라우저: 탭을 열어 둔 상태에서 원본 수정과 웹훅을 실행하고 새로고침/화면 이동/뒤로가기 결과를 비교한다.
- [ ] Vercel: 별도 검증 배포에서 동일 시나리오를 실행하고 원본 로그와 Runtime Logs를 대조한다. 로컬 결과를 CDN·다중 인스턴스 검증으로 대체하지 않는다.
- [ ] 이미지: 같은 URL 교체와 버전 URL 교체를 비교해 본문 태그와 이미지 캐시가 별개임을 확인한다.
