# UI/UX 자료 조사와 콘텐츠 방향

## 조사 범위

- 조사일: 2026-09-21
- 대상: 개발자가 읽는 HEAP-FORGE UI/UX 탭
- 단계: 문헌 조사와 콘텐츠 제안. 화면 개편, 공개 글 발행, 실험 실행은 아직 하지 않았다.
- 예상 독자는 UI를 구현하거나 디버깅하는 개발자다. 실제 독자 조사로 확정한 페르소나는 아니다.

## 핵심 개념

예쁜 화면 모음보다 사용자가 작업을 끝낼 수 있는 인터페이스를 구현하고 검증하는 자료가 현재 콘텐츠에 더 잘 맞는다. 이는 아래 자료와 기존 글을 바탕으로 한 프로젝트 제안이지, 특정 레이아웃의 성과를 입증한 사용자 실험 결과가 아니다.

Web은 실행 원리와 성능, UI/UX는 조작·인지·오류 복구를 설명하는 방향을 제안한다. 같은 Dialog를 다루더라도 UI/UX에서는 포커스 이동과 작업 복귀를 핵심 질문으로 삼는다.

## 자료에서 확인한 기준

| 우선순위 | 독자가 가진 문제                              | 원문에서 확인할 내용                                                                                                                                                                        | 제안하는 결과물                          |
| -------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 1        | 창을 닫았는데 키보드 위치를 잃었다            | [WAI APG 모달 Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)의 초기 포커스·Tab 순환·닫기·복귀 규칙                                                                         | 재현 가능한 포커스 사례와 수정 전후 비교 |
| 2        | 입력이 틀렸다고만 나오고 고칠 방법을 모르겠다 | [GOV.UK 오류 복구](https://design-system.service.gov.uk/patterns/validation/)와 [오류 요약](https://design-system.service.gov.uk/components/error-summary/)의 입력 보존·필드 연결·오류 안내 | 제출 실패 후 입력을 유지하며 수정하는 폼 |
| 3        | 검색이 끝났는지 실패했는지 알 수 없다         | [WCAG 2.2 상태 메시지 해설](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)의 포커스를 옮기지 않는 상태 전달                                                              | 로딩·성공·0건·실패 상태 비교와 안내 실험 |
| 4        | 확대하면 잘리고 고정 바가 조작 대상을 가린다  | [Reflow 해설](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [Focus Not Obscured 해설](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)              | 긴 제목·확대·고정 헤더/하단 바 검증 사례 |

자료의 성격을 구분한다. WCAG 성공 기준은 목표를 정의하고 Understanding 문서는 해설한다. APG는 구현 패턴 지침이며, GOV.UK는 특정 서비스 디자인 시스템의 운영 지침이다. 예를 들어 GOV.UK의 검증 시점을 모든 제품의 보편적 의무로 옮기지 않는다.

## 프로젝트에서 배운 점

직전 로컬 화면 검토에서는 실제 상세 글 2개와 피드로 이동하는 예시 카드 5개가 표시됐다. 원격 콘텐츠를 포함한 운영 환경의 글 수를 의미하지 않는다.

- 기존 `Focus Management 체크리스트`와 ARIA 사례는 첫 심화 콘텐츠의 출발점이 된다.
- 글 순서에 따라 붙는 케이스 스터디·리서치·튜토리얼 라벨은 자료의 실제 유형을 설명하지 못한다.
- 글이 없는데 완성된 글처럼 보이는 카드를 채우지 않는다. 계획은 별도 운영 문서에서 관리하고 공개 목록에는 실제 글만 노출하는 방향을 제안한다.
- NN/g의 [Information Scent](https://www.nngroup.com/articles/information-scent/)는 링크 제목과 요약이 목적지의 내용을 판단할 단서를 제공해야 한다고 설명한다. 따라서 추상적인 주제명 대신 문제·대상·해결 범위를 카드에서 드러내는 구성을 제안한다.

## 첫 심화 자료 제안

가제: **닫았는데, 어디로 돌아가야 하지?**

보조 제목: Dialog·Drawer의 포커스 복귀를 재현하고 점검하기.

기존 ARIA 글을 다음 순서로 보강한다. 아래는 계획이며 아직 측정 결과가 아니다.

1. 사용자 문제: 마우스로는 정상처럼 보이지만 키보드로 다음 동작을 이어가기 어려운 상황을 설명한다.
2. 최소 재현: 열기 버튼, 모달, 다음 입력 하나만 둔다. 앱의 전체 레이아웃은 제거한다.
3. 기대 동작: 열기·Tab·Shift+Tab·Escape·닫기 후 이동을 표로 정의한다.
4. 상태 관측: `focusin`, `document.activeElement`, 열림 상태, DOM 제거 시점, `inert`/`aria-hidden` 범위를 함께 기록한다. 입력값이나 개인 정보는 기록하지 않는다.
5. 가설 분리: DOM 제거, 포커스 복귀 처리, 애니메이션 유무를 한 번에 하나씩 바꾼다. 임의 timeout이나 콘솔 경고 숨김을 해결책으로 삼지 않는다.
6. 대안 비교: 네이티브 `<dialog>`와 프로젝트에서 실제 사용하는 라이브러리를 같은 시나리오로 비교한다. 라이브러리·브라우저 버전과 모달 설정을 기록한다.
7. 예외: trigger가 삭제되는 경우, 긴 내용, 파괴적 동작, reduced-motion 상태를 다룬다.
8. 검증: 자동화로 잡은 범위와 수동 키보드·스크린 리더 확인 결과를 구분해 남긴다.

### 기존 글을 보강할 때 주의할 점

- 모달과 비모달을 구분한다. [MDN Popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API)의 네이티브 popover는 비모달이다. 모든 Popover·Drawer에 동일한 focus trap을 적용한다고 설명하지 않는다.
- 모달의 초기 포커스는 항상 첫 input일 필요가 없고, 종료 후에도 항상 기존 trigger가 정답인 것은 아니다. APG가 설명하는 콘텐츠와 작업 흐름에 따른 예외를 포함한다.
- 기존 글의 애니메이션 종료 후 이동 방식은 해당 구현의 가설로 다시 검증한다. 특정 라이브러리의 현재 복귀 동작을 확인하지 않고 보편적 해결책으로 제시하지 않는다.
- [APG Dialog 예제](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/dialog/)도 운영 환경에 그대로 사용할 코드가 아니라고 경고한다. 참고 구현과 검증된 제품 코드를 구분한다.
- [Playwright 접근성 테스트 문서](https://playwright.dev/docs/accessibility-testing)는 자동 검사와 수동·사용자 검증의 병행을 권고한다. axe 오류 0개를 접근성 전체 통과로 표시하지 않는다.

## 독자에게 필요한 정보

| 읽기 단계 | 독자가 판단할 것                       | 제공할 정보                                              |
| --------- | -------------------------------------- | -------------------------------------------------------- |
| 목록      | 내 문제와 관련 있는가                  | 구체적인 제목, 증상 한 줄, 대상 컴포넌트, 실제 자료 유형 |
| 도입      | 이 방법을 내 환경에 써도 되는가        | 문제 범위, 선행 지식, 버전, 적용 제외 조건               |
| 본문      | 왜 문제가 생기고 무엇을 바꿔야 하는가  | 최소 재현, 상태 흐름, 대안과 단점, 핵심 수정 코드        |
| 검증      | 수정한 뒤 무엇을 확인할 것인가         | 키보드 절차, 자동 테스트, 수동 검증 범위, 알려진 한계    |
| 마무리    | 다시 점검하거나 더 깊게 읽을 수 있는가 | 체크리스트, 직접 근거가 되는 원문 링크, 확인 날짜        |

## 화면 구성 제안

현재 토큰과 공용 카드 시스템을 유지하되 콘텐츠 정보의 우선순위를 바꾼다. 다음 구조는 미구현 제안이다.

```text
UI/UX
사용하기 좋은 인터페이스를 만들고 확인하는 기록

[전체] [포커스와 키보드] [입력과 오류] [상태 안내]
※ 실제 공개 자료가 있는 주제만 표시

닫았는데, 어디로 돌아가야 하지?
Dialog를 닫은 뒤 포커스를 잃는 상황을 재현하고 복귀 위치를 비교합니다.
접근성 · 구현 사례
데모/체크리스트 링크는 실제 제공할 때만 표시

관련 공개 글 목록
```

- 목록은 큰 썸네일보다 제목·증상·자료 유형을 우선하는 1열 목록을 기본 후보로 삼는다. 이미지는 실제 문제 화면이나 동작 비교에 도움이 될 때만 작은 미리보기로 사용한다.
- 상단에 강조하는 심화 글은 하나만 두고, 같은 글을 아래 목록에 다시 중복하지 않는다. 검수 중인 가제는 발행 전까지 공개 카드로 만들지 않는다.
- 자료 유형은 사례·가이드·체크리스트 등 작성자가 실제 내용에 맞게 지정한다. 검증 완료 같은 포괄적 배지보다 확인한 환경과 날짜를 상세에 적는다.
- 상세에서는 재현 → 이유 → 수정 → 검증을 주된 읽기 순서로 삼는다. 근거와 코드를 숨기는 대신 긴 로그·보충 자료만 접는다.
- 수정 전후 데모는 한 번에 하나씩 실행하고, 키보드 탈출과 초기화 수단을 제공한다. 애니메이션 자동 재생이나 고의로 탈출할 수 없는 포커스 함정은 만들지 않는다.
- 모바일은 가로 스크롤 없이 필터가 줄바꿈되게 하고, 비교 UI는 세로로 배치한다. 색상만으로 실패/성공을 구분하지 않는다.

## 적용 조건과 다음 검증

보기 좋은 정도는 스크린샷만으로 결정하지 않는다. 실제 대상 독자에게 다음 과제를 주는 형성적 사용성 검토를 제안한다.

- 자신이 겪은 UI 문제에 맞는 글을 찾을 수 있는가?
- 클릭 전에 제공되는 결과물과 필요한 환경을 설명할 수 있는가?
- 예제를 따라 한 뒤 수정 성공 여부를 스스로 확인할 수 있는가?
- 모바일·확대 화면·키보드 조작에서도 같은 과제를 끝낼 수 있는가?

첫 클릭의 적합성, 목적지 기대와의 불일치, 과제 완료 여부를 기록한다. 독자 표본이나 실험을 아직 확보하지 않았으므로 성공률·소요 시간 개선을 주장하지 않는다.

후속 조사 후보는 검색·필터 URL 상태, 로딩 중 중복 제출, 명암·모션이다. 처음부터 빈 분류를 모두 만들기보다 첫 심화 글을 검증한 뒤 실제 글 수에 맞춰 확장한다.
