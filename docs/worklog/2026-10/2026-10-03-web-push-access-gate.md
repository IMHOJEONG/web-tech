# 웹 푸시 실험의 초대 접근 제한

## Summary

기본 비활성화를 유지하면서 초대받은 참여자만 구독 BFF를 사용할 수 있도록 했다. 실제 Production WAF는 CLI 인증 만료로 게시하지 못했으며 활성화 조건·검증·복구 절차를 남겼다.

## Changed

- config·구독 등록/해지를 NAS에 전달하기 전에 1시간짜리 HMAC 세션을 확인한다. 쿠키는 HttpOnly·SameSite=Strict이고 운영에서는 Secure이다.
- 초대 코드와 서명 키를 분리하고 비활성·미설정·공용 키·운영 WAF 미확인 상태를 거부한다. `.env.example`의 플래그는 false, 비밀값은 공란을 유지한다.
- 참여 코드 폼을 역할별 컴포넌트로 분리하고 한·영 안내·개인정보 안내를 추가했다. 코드 확인만으로 알림 권한을 요청하지 않는다.
- [ADR-0010](../../architecture/adr-0010-web-push-invitation-and-waf-gate.md)에 결정과 공유 초대 코드의 한계를 기록했다.
- [실행 절차](../../runbooks/docs-web-push-experiment.md)에 전체 푸시 경로 IP 10회/60초 WAF 규칙, 프로젝트·기존 draft 확인, 제한 규칙 충돌, 활성화·중단 순서를 추가했다.
- 단위 테스트·실제 BFF·모바일 UI 및 초대 인증 후 실제 Chrome 연동을 검증했다. [결과와 증거](../../verification/push/2026-10-03-push-access-gate.md): 공용 로직 198개, 브라우저 11개, 타입 검사·변경 파일 lint 통과; 실제 수신 1건과 해지 확인.

## Notes

- 실제 비밀값·구독 주소·쿠키를 Git이나 결과에 남기지 않았다. 기존 환경 파일·운영 NAS·Vercel 설정은 변경하지 않았다.
- 코드 공개는 기능 활성화가 아니다. 운영에서는 두 활성화 설정과 WAF 검증 확인 값이 필요하다. WAF 확인 플래그는 자동 검사기가 아니라 운영자 확인이다.
- 세션 만료·코드 교체는 기존 구독을 삭제하지 않는다. 공유 코드에는 개별 사용자 식별·회수·quota가 없다.
- Vercel CLI의 `whoami`가 유효하지 않은 토큰으로 실패했다. WAF를 적용했다고 표시하지 않는다.
- 운영자가 WAF를 직접 변경하기로 했다. Dashboard 설정과 게시·검증 방법을 안내하며 원격 설정을 대신 변경하지 않는다.

## Open Questions

- docs 프로젝트의 실제 WAF 한도와 기존 revalidation 규칙 사용 여부는 로그인 갱신 후 확인해야 한다. Hobby의 한 개 제한이면 기존 보호를 유지하고 푸시 활성화를 보류한다.
- 공개 서비스로 확장할 때 개인 초대·인증·분산 quota를 도입할 시점은 별도 결정한다.
