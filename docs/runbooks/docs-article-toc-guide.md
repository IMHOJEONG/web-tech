# 블로그 본문 목차 작성·연결 가이드

## 목적과 준비 조건

글 작성자는 본문의 제목만 작성하고, 앱은 제목에서 목차를 추출한다. 목차 링크를 글마다 직접 만들거나 스크롤 코드를 복제하지 않는다.

- 대상: `apps/docs` 로컬 MDX와 원격 Markdown에서 생성된 HTML. 2026-11-14 기능 브랜치의 공통 UI를 기준으로 하며 main 병합·운영 배포는 별도다.
- 예제: [합성 Markdown](../../apps/docs/widgets/article-toc/examples/article.md), [타입 검사되는 옵션 코드](../../apps/docs/widgets/article-toc/examples/toc-options.ts). 실제 글·NAS 데이터가 아니며 공개 목록에 자동 등록되지 않는다.
- 검사 환경: 저장소가 고정한 Node 24·pnpm과 설치된 workspace 의존성. 원격 토큰은 필요 없다.
- 이 가이드의 추가 예제는 운영 문서다. 새 글의 공개 검수·게시 승인을 대신하지 않는다.

## 실행 순서

### 1. 독자가 찾을 질문으로 제목을 작성한다

페이지 제목은 frontmatter `title`, 본문 큰 단락은 `##`, 세부 설명은 `###`, 꼭 필요한 하위 단계만 `####`로 작성한다.

```markdown
## 문제를 확인하는 방법

### 관측할 값

### 비교 조건

#### 결과를 읽는 순서

## 적용 전 점검

## 참고 자료
```

- `개요`, `내용`만 반복하기보다 제목만 읽어도 찾을 내용을 알 수 있게 쓴다. 시각적 크기를 바꾸려고 heading 단계를 건너뛰지 않는다.
- 본문 H1은 기본 목차에서 제외된다. H1 자체는 기존 정책상 경고이며, 자동으로 H2로 바꾸거나 게시를 차단하지 않는다.
- H2 다음 H4처럼 단계를 두 칸 이상 건너뛰면 본문 검사에 실패한다. 제목의 H2/H3/H4 계층과 화면의 들여쓰기가 연결된다.
- 긴 제목은 펼친 목록에서 줄바꿈된다. 접힌 summary의 현재 제목만 한 줄로 줄여 보인다. 제목 길이를 자동으로 게시 차단하지는 않는다.
- 목차를 만들기 위해 본문에 `## 목차`와 링크 목록을 따로 넣지 않는다. 실제 설명에 필요한 소제목만 작성한다.
- 코드 펜스 안의 `##`는 코드 예시이며 목차 제목이 아니다. 짧은 글을 목차 때문에 인위적으로 잘게 나누지 않는다.

### 2. 로컬·원격의 추출 경계를 확인한다

| 경로                 | 목차 입력과 현재 범위                                                               | 작성 시 주의점                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 로컬 runtime MDX     | `renderArticleContent`의 remark 목차와 heading transform. 기본적으로 Markdown H2~H6 | JSX 제목은 Markdown 제목과 같은 목차 등록을 보장하지 않는다. 동적으로 만든 제목·ID에 의존하지 않는다. |
| 원격 Markdown → HTML | 백엔드가 HTML을 만들고 프론트가 H1~H4에서 목차를 추출. 공통 필터가 H1 제외          | 양쪽에 같은 계층을 원하면 H2~H4를 사용한다. 원격 H5/H6까지 추출한다고 가정하지 않는다.                |

UI 공유는 두 렌더러의 ID 생성 규칙까지 동일하다는 뜻이 아니다. 원격 HTML에 기존 ID가 있으면 보존되지만, ID가 없는 중복 제목의 충돌을 이 UI가 해결하지 않는다. 같은 이름을 반복해야 하면 맥락을 붙여 구분하고, 이미 공유된 fragment는 실제 상세에서 검증한다. 제목을 변경했다고 모든 과거 링크가 자동 보존되는 것은 아니다. 로컬 ID 할당의 세부 기준은 [ADR-0027](../architecture/adr-0027-article-heading-anchor-compatibility.md)을 따른다.

### 3. 앱에서는 기존 공통 레이아웃을 사용한다

글 작성자는 React 코드를 추가할 필요가 없다. 상세 페이지를 구현할 때도 `ArticleContentLayout`에 기존 렌더 결과의 `toc`를 전달하는 흐름을 먼저 재사용한다. API 요청이나 렌더러를 목차 컴포넌트 안에서 다시 실행하지 않는다.

특수한 화면에 `Toc`만 연결해야 한다면 아래처럼 예제 옵션을 참고한다. 이는 설명용 사용 코드이며 실제 레이아웃의 중복 구현을 추가하라는 뜻은 아니다. `toc`와 `title`은 기존 렌더러·번역에서 전달받는다.

```tsx
import Toc from '~/widgets/article-toc/ui/toc'
import {
    desktopTocOptions,
    mobileTocOptions,
} from '~/widgets/article-toc/examples/toc-options'

<Toc toc={toc} title={title} {...desktopTocOptions} />
<Toc toc={toc} title={title} {...mobileTocOptions} />
```

위 import는 docs 앱의 `~` 별칭 기준이다. 예제 옵션은 참고용이며 production에서 불필요하게 예제 파일을 의존하지 말고 필요한 정책만 기존 레이아웃에 반영한다. 한 화면에 두 목록을 그대로 동시에 표시하지 말고 데스크톱/모바일 가시성 분리를 유지한다. 제목 ID가 있는 본문 DOM도 함께 렌더되어 있어야 한다.

| 옵션              | 기본값  | 사용 기준                                                                           |
| ----------------- | ------- | ----------------------------------------------------------------------------------- |
| `maxDepth`        | 6       | 예제는 로컬·원격의 공통 범위인 4로 제한한다. 앱 전체 기본값을 바꾸는 설정은 아니다. |
| `skipLevels`      | `[1]`   | H1 제외. 추가 수준을 제외하면 계층 일부가 사라질 수 있다.                           |
| `indented`        | `true`  | 표시된 가장 얕은 제목을 기준으로 상대 들여쓰기.                                     |
| `defaultOpen`     | `true`  | 모바일 예제는 `false`. 초기값이며 prop 변경으로 상태를 동기화하는 API가 아니다.     |
| `closeOnNavigate` | `false` | 모바일은 `true`. 선택 후 닫기·본문 제목 focus·Escape 복귀를 함께 사용한다.          |
| `exclude`         | 없음    | 제목 텍스트에 적용할 정규식 문자열. 임의 사용자 검색어를 그대로 넘기지 않는다.      |

서버에서 빈 영역을 판단할 때와 클라이언트에 같은 필터 옵션을 전달한다. 하나만 다르면 빈 aside나 내용 없는 접기 영역이 남는다. `ordered`·`tight`는 기존 호환 옵션이며 기본 화면에는 번호·촘촘한 행을 추가하지 않는다.

### 4. 예제와 실제 글을 검사한다

저장소 루트에서 실행한다.

```sh
pnpm --filter docs typecheck:node-test
pnpm --filter docs exec node --experimental-strip-types --test lib/article-toc-guide.test.ts
pnpm --filter docs validate:content
```

첫 두 명령은 예제 옵션의 타입과 합성 문서의 작성 규칙·실제 로컬 목차/본문 앵커·원격 추출 한계를 검사한다. `validate:content`는 블로그의 실제 콘텐츠 폴더 검사이며 위젯의 `examples`를 게시 대상으로 추가하지 않는다.

UI 변경까지 함께 검토할 때는 [공통 목차 검증 보고서](../verification/accessibility/2026-11-14-article-toc-ux.md)의 브라우저 회귀 명령을 사용한다. 원격 문서 수정 후 운영 반영에는 기존 게시·revalidation 절차가 별도로 필요하며, 이 가이드를 작성하는 작업에서는 호출하지 않는다.

## 기대 결과

- 데스크톱은 얇은 가이드와 현재 제목을 표시하고, 모바일은 기본 접힌다. 항목 수는 필터를 통과한 제목 수다.
- 현재 항목만 `aria-current="location"`을 가지며 수동 스크롤은 URL hash를 덮어쓰지 않는다. 위치 표시는 읽기 완료율이 아니다.
- 선택 시 기존 hash로 이동하고 sticky header 여백을 유지한다. 모바일은 닫은 뒤 해당 제목으로 focus를 옮기며 Escape는 summary로 복귀한다.
- 모션 감소 환경에서는 부드러운 스크롤·전환을 줄인다. 긴 목록은 목차 안에서 세로 스크롤되고 가로 스크롤은 만들지 않는다.
- 표시할 제목이 없으면 공통 레이아웃이 목차 영역을 만들지 않는다.

## 실패 대응과 복구

1. 항목이 없으면 H2~H4가 실제 본문 제목인지, 코드 펜스 안인지, 필터에서 제외됐는지 확인한다.
2. 클릭이 안 되면 생성된 `href`와 본문 `id`를 비교한다. 한글·번호·문장부호를 포함한 ID를 추측해서 손으로 만들지 않는다.
3. 현재 위치가 맞지 않으면 제목 DOM·헤더 높이·이미지 또는 글꼴 로딩 후 배치를 확인한다. 늦게 새로 삽입되는 동적 제목의 자동 등록은 보장하지 않는다.
4. 중복 제목·원격 H5/H6 차이는 작성 구조나 렌더러의 문제로 분리한다. UI 가이드 추가만으로 NAS HTML을 수정하거나 기존 ID를 일괄 변경하지 않는다.
5. 검증에 실패한 예제는 게시하지 않는다. 실제 글의 잘못된 계층을 고치고 다시 검사하며 검사 기준을 낮추지 않는다.
