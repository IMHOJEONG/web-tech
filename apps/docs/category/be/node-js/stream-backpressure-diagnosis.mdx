## 메모리가 오른다고 바로 누수일까요

파일을 압축하거나 큰 응답을 전송하는 Node.js 프로세스의 메모리가 계속 오른다면 누수를 먼저 의심하기 쉽습니다. 하지만 생산자(producer)가 소비자(consumer)보다 빠르게 데이터를 만드는데도 속도를 늦추지 않았다면, 처리되지 않은 청크가 메모리에 쌓이고 있을 수 있습니다.

백프레셔(backpressure)는 느린 소비자가 빠른 생산자에게 잠시 기다리라는 신호를 보내는 흐름 제어 방식입니다. 데이터가 어느 순간부터 쌓이는지 찾으려면 힙 사용량만 보지 말고 Writable 스트림의 버퍼 상태와 `write()` 반환값을 함께 관찰해야 합니다.

## 먼저 스트림 용어부터 알아보기

스트림(stream)은 큰 데이터를 한 번에 메모리에 올리지 않고 작은 조각으로 나누어 처리하는 방식입니다. 예를 들어 1 GB 로그 파일을 읽어 압축한다고 가정해 보겠습니다. 파일 전체를 먼저 읽는 대신, 일부를 읽고 압축한 뒤 다음 일부를 계속 처리할 수 있습니다.

이 글에서 사용하는 용어를 먼저 정리하면 다음과 같습니다.

| 용어                   | 의미                                                           | Node.js 예시                              |
| ---------------------- | -------------------------------------------------------------- | ----------------------------------------- |
| 생산자(producer)       | 데이터를 만들어 다음 단계로 보내는 쪽입니다.                   | 파일을 읽는 `createReadStream()`          |
| 소비자(consumer)       | 전달받은 데이터를 처리하는 쪽입니다.                           | 파일을 쓰는 `createWriteStream()`         |
| 청크(chunk)            | 스트림이 한 번에 전달하는 데이터 조각입니다.                   | 파일에서 읽은 `Buffer` 한 조각            |
| 버퍼(buffer)           | 바로 처리하지 못한 청크가 잠시 기다리는 메모리 공간입니다.     | Writable 스트림의 내부 쓰기 대기열        |
| 백프레셔(backpressure) | 소비자가 밀렸을 때 생산자에게 잠시 멈추라고 보내는 신호입니다. | `write()`의 `false` 반환과 `drain` 이벤트 |

### Readable과 Writable의 차이

Readable 스트림은 데이터를 꺼내 읽을 수 있는 출발점입니다. 파일을 읽는 `fs.createReadStream()`, HTTP 요청 본문을 받는 `IncomingMessage`가 대표적인 예입니다.

Writable 스트림은 데이터를 받아 최종 목적지로 보내는 도착점입니다. 파일을 쓰는 `fs.createWriteStream()`, HTTP 응답을 보내는 `ServerResponse`, TCP 소켓이 여기에 해당합니다.

Transform 스트림은 데이터를 받는 동시에 변환한 결과를 다시 내보냅니다. gzip 압축 스트림처럼 Writable과 Readable의 성격을 모두 가집니다.

앞 단계가 데이터를 만드는 속도보다 다음 단계가 처리하는 속도가 느리면 중간 버퍼가 차기 시작합니다. Node.js 스트림은 이때 백프레셔 신호를 사용해 앞 단계를 잠시 멈춥니다.

## `write()`의 반환값부터 확인하기

Writable 스트림의 `write(chunk)`는 청크를 더 받을 수 있으면 `true`를 반환합니다. 내부 버퍼가 `highWaterMark`에 도달했거나 이를 넘어서 기다려야 한다면 `false`를 반환합니다.

`false`는 쓰기에 실패했다는 뜻이 아닙니다. 쓰기 요청은 수락되었지만 아직 완료된 것은 아니므로, 이후 데이터를 계속 밀어 넣지 말고 `drain` 이벤트를 기다리라는 신호입니다.

```ts
import { once } from 'node:events'
import type { Writable } from 'node:stream'
import { finished } from 'node:stream/promises'

async function writeWithBackpressure(
    writable: Writable,
    chunks: Iterable<Buffer>
): Promise<void> {
    for (const chunk of chunks) {
        if (!writable.write(chunk)) {
            await once(writable, 'drain')
        }
    }

    writable.end()
    await finished(writable)
}
```

`writable: Writable`은 데이터를 받는 목적지의 타입입니다. `Iterable<Buffer>`는 `Buffer` 청크를 `for...of`로 하나씩 꺼낼 수 있는 배열 같은 입력을 뜻합니다. `Promise<void>`는 비동기 처리가 끝나면 별도의 결과값 없이 완료된다는 뜻입니다.

`write()`가 계속 `false`를 반환하는데도 반복문을 멈추지 않으면 Node.js는 이후에 전달된 청크까지 버퍼에 보관합니다. 소비자가 처리 속도를 따라잡지 못하는 동안 버퍼에 쌓인 데이터가 늘어나며, 메모리 사용량과 가비지 컬렉션 비용도 함께 커질 수 있습니다.

> [!WARNING]
> `write()`가 `false`를 반환한 뒤에도 계속 쓰면 느린 디스크뿐 아니라 상대가 데이터를 읽지 않는 TCP 소켓에서도 같은 문제가 발생할 수 있습니다. 생산자가 외부 입력을 제한 없이 받아들이면 메모리 부족을 넘어 서비스 가용성 문제로 이어질 수 있습니다.

이 글에서는 Node.js 24의 클래식 스트림을 기준으로 설명합니다. Web Streams나 `node:stream/iter`의 별도 백프레셔 정책에까지 이 설명을 그대로 일반화하지는 않습니다.

## `highWaterMark`는 메모리 상한이 아닙니다

`highWaterMark`라는 이름 때문에 전체 메모리 사용량을 제한하는 값으로 오해하기 쉽습니다. 이 값은 스트림이 백프레셔를 적용하기 시작하는 버퍼 임계값이며, 엄격한 최대 용량을 보장하지는 않습니다.

`highWaterMark`를 물류 창고의 “추가 입고를 멈추는 기준선”이라고 생각하면 이해하기 쉽습니다. 기준선까지 상자가 들어오면 입고 담당자에게 잠시 기다리라고 알리지만, 창고의 벽이 생겨 상자가 절대로 더 들어오지 못하게 만드는 값은 아닙니다. 생산자가 신호를 무시하고 계속 쓰면 Node.js는 뒤따르는 청크도 메모리에 보관할 수 있습니다.

바이트 모드에서는 보통 바이트 수를, 객체 모드에서는 객체 수를 기준으로 삼습니다. Node.js 24의 기본값은 일반 Writable 스트림에서 64 KiB, 객체 모드에서 16개입니다. 다만 스트림 구현과 생성 옵션에 따라 달라질 수 있으므로 실행 중인 객체의 값을 직접 확인하는 편이 안전합니다.

예를 들어 `highWaterMark`가 64 KiB이고 한 청크가 32 KiB라면 다음 흐름을 예상할 수 있습니다.

1. 첫 번째 32 KiB 청크를 쓰면 대기량이 32 KiB가 되고 `write()`는 `true`를 반환할 수 있습니다.
2. 두 번째 청크까지 들어와 대기량이 64 KiB에 도달하면 `write()`가 `false`를 반환합니다.
3. 생산자는 추가 쓰기를 멈추고 `drain`을 기다립니다.
4. 소비자가 버퍼를 처리하면 `drain`이 발생하고 생산자가 다시 쓰기 시작합니다.

여기서 64 KiB는 프로세스 전체 메모리 제한이 아닙니다. 해당 Writable 스트림이 추가 쓰기를 늦추도록 신호를 내는 기준입니다.

다음 공개 속성으로 상태를 관찰할 수 있습니다.

| 속성                    | 확인할 내용                                       |
| ----------------------- | ------------------------------------------------- |
| `writableHighWaterMark` | 백프레셔 신호를 내기 시작하는 임계값              |
| `writableLength`        | 아직 쓰기가 완료되지 않은 바이트 또는 객체 수     |
| `writableNeedDrain`     | 버퍼가 찼고 이후 `drain`을 기다리는 상태인지 여부 |

`writableLength`가 반복해서 임계값 근처까지 올라갔다가 내려온다면 스트림이 속도 차이를 흡수하는 정상적인 모습일 수 있습니다. 반대로 처리량이 일정한데도 오랫동안 내려오지 않고 `writableNeedDrain` 상태가 계속 유지된다면 소비자 병목이나 백프레셔 신호를 무시하는 코드를 조사해야 합니다.

## 느린 소비자를 만들어 관찰하기

아래 예제는 각 청크를 20ms 뒤에 처리하는 Writable 스트림을 만듭니다. 빠른 생산자가 32 KiB 청크를 연속으로 쓰기 때문에 작은 `highWaterMark`에서도 백프레셔를 쉽게 확인할 수 있습니다.

Writable의 `write(_chunk, _encoding, callback)` 구현은 청크 처리가 끝났을 때 `callback`을 호출해야 합니다. 이 예제에서는 `setTimeout`으로 호출을 20ms 늦춰 느린 소비자를 의도적으로 만듭니다.

아래 코드를 `backpressure-demo.mts`로 저장한 뒤 `node backpressure-demo.mts`로 실행할 수 있습니다. `.mts`는 ES 모듈 방식의 TypeScript 파일입니다. 이 글에서 확인한 Node.js v24.12.0은 타입 표기를 제거하고 직접 실행하므로 이 예제에는 별도 변환 도구가 필요하지 않습니다. 다만 Node.js 자체가 타입 오류를 검사하지는 않습니다. 타입 검사는 TypeScript의 `tsc --noEmit`으로 별도로 수행합니다.

```ts
import { once } from 'node:events'
import { Writable } from 'node:stream'
import { finished } from 'node:stream/promises'

const slowSink = new Writable({
    highWaterMark: 64 * 1024,
    write(
        _chunk: Buffer,
        _encoding: BufferEncoding,
        callback: (error?: Error | null) => void
    ) {
        setTimeout(callback, 20)
    },
})

const chunk = Buffer.alloc(32 * 1024)

for (let index = 0; index < 6; index += 1) {
    const canContinue = slowSink.write(chunk)

    console.log({
        index,
        canContinue,
        buffered: slowSink.writableLength,
        needDrain: slowSink.writableNeedDrain,
    })

    if (!canContinue) {
        await once(slowSink, 'drain')
        console.log('drain')
    }
}

slowSink.end()
await finished(slowSink)
console.log('finish')
```

`BufferEncoding`은 인코딩 이름의 타입이고, `callback: (error?: Error | null) => void`는 오류를 선택적으로 전달하는 완료 함수의 타입입니다. 이 예제는 `Buffer`를 사용하므로 `_encoding` 값을 사용하지 않습니다. `const chunk`와 `const canContinue`의 타입은 각각 `Buffer`와 `boolean`으로 자동 추론됩니다.

Node.js v24.12.0에서 TypeScript 예제를 직접 실행하면 다음 순서로 출력됩니다.

```text
$ node backpressure-demo.mts
{ index: 0, canContinue: true, buffered: 32768, needDrain: false }
{ index: 1, canContinue: false, buffered: 65536, needDrain: true }
drain
{ index: 2, canContinue: true, buffered: 32768, needDrain: false }
{ index: 3, canContinue: false, buffered: 65536, needDrain: true }
drain
{ index: 4, canContinue: true, buffered: 32768, needDrain: false }
{ index: 5, canContinue: false, buffered: 65536, needDrain: true }
drain
finish
```

이 예제에서는 전체 실행 시간보다 상태가 변하는 순서를 확인해야 합니다.

1. `index: 0`에서는 아직 쓰기가 완료되지 않은 데이터가 32 KiB이므로 `canContinue`가 `true`입니다.
2. `index: 1`에서는 대기량이 64 KiB에 도달해 `canContinue`가 `false`, `needDrain`이 `true`가 됩니다.
3. 코드가 `drain`을 기다리는 동안 느린 소비자가 두 청크를 처리합니다.
4. `drain` 뒤에는 대기량이 줄어 생산자가 다음 청크를 쓰기 시작합니다.
5. 마지막 `finish`는 `end()` 이후 남은 청크까지 모두 처리했다는 뜻입니다.

실제 값과 로그 형태는 Node.js 버전, 실행 환경, 청크 크기와 처리 지연에 따라 달라질 수 있습니다. 특정 로그 행 수에 맞추기보다 `false → 대기 → drain → 재개` 순서가 나타나는지 확인해 보세요.

## 직접 연결할 때보다 `pipeline()`을 우선하기

Readable, Transform, Writable 스트림을 연결한다면 각 단계의 `write()`와 `drain`을 직접 조정하기보다 `stream.pipeline()`을 먼저 고려해 보세요. `pipe()`와 `pipeline()`은 하위 스트림이 느릴 때 상위 스트림의 읽기 속도를 조절합니다. `pipeline()`은 여기에 더해 여러 스트림의 오류 전파와 정리 작업도 한곳에서 처리합니다.

```ts
import { createReadStream, createWriteStream } from 'node:fs'
import { pipeline } from 'node:stream/promises'
import { createGzip } from 'node:zlib'

await pipeline(
    createReadStream('access.log'),
    createGzip(),
    createWriteStream('access.log.gz')
)
```

`pipeline()`을 사용했다고 모든 메모리 증가가 사라지는 것은 아닙니다. Transform 내부에서 콜백이 늦어지면 처리량과 지연 시간에 영향을 주지만, 정상적인 파이프라인은 그 속도 차이를 상위 스트림에 전달합니다. 다만 별도의 비동기 작업을 제한 없이 만들거나 스트림 바깥 배열에 청크를 계속 보관한다면 메모리 문제가 남을 수 있습니다.

## Next.js 스트리밍과는 어디에서 만날까요

Next.js App Router도 페이지 전체가 완성될 때까지 기다리지 않고 준비된 화면부터 브라우저로 보낼 수 있습니다. `loading.tsx`나 `<Suspense>`의 `fallback`을 먼저 보여주고, 느린 데이터가 준비되면 나머지 화면을 이어서 보내는 방식입니다. 이를 흔히 Next.js Streaming이라고 부릅니다.

여기에는 서로 다른 두 종류의 “기다림”이 있습니다.

- `<Suspense>`는 아직 데이터나 렌더링 결과가 준비되지 않았을 때 어느 UI를 먼저 보여줄지 결정합니다.
- Node.js의 백프레셔는 이미 만들어진 HTML 같은 데이터가 소비자의 처리 속도보다 빠르게 전송되지 않도록 조절합니다.

두 개념은 같은 기능을 하지는 않지만, 서버에서 브라우저까지 이어지는 하나의 요청 처리 흐름 안에서 함께 작동합니다.

```text
데이터 준비
   │
   ▼
Suspense 경계 ── 준비된 화면과 fallback을 구분
   │
   ▼
React·Next.js ── HTML 또는 화면 데이터 조각 생성
   │
   ▼
HTTP 응답 스트림 ── 런타임 어댑터를 거쳐 네트워크로 전송
   │
   ▼
브라우저
```

예를 들어 본문은 바로 준비되지만 관련 글 목록은 데이터 요청 때문에 늦는 페이지를 생각해 보겠습니다. 다음 코드는 전체 앱을 그대로 실행하는 예제가 아니라, 두 영역을 Suspense로 나누는 구조를 보여주는 개념 예제입니다. 여기서는 `RelatedArticles`가 데이터를 기다리는 async Server Component여서 렌더링 중 suspend한다고 가정합니다. 클라이언트의 Effect나 이벤트 핸들러에서 시작한 요청은 그 자체로 이 Suspense fallback을 활성화하지 않습니다.

```tsx
import { Suspense } from 'react'

export default function ArticlePage() {
    return (
        <main>
            <ArticleBody />
            <Suspense fallback={<p>관련 글을 불러오는 중입니다.</p>}>
                <RelatedArticles />
            </Suspense>
        </main>
    )
}
```

`ArticleBody`가 준비되어 있고 `RelatedArticles`가 렌더링 중 suspend하면, React는 본문과 fallback으로 구성된 셸(shell)을 먼저 만들 수 있습니다. 여기서 셸은 사용자가 먼저 볼 수 있는 페이지의 기본 뼈대입니다. 관련 글 데이터가 준비되면 React가 추가 렌더링 결과를 만들고 Next.js가 뒤이어 전송할 수 있습니다. Server Component를 사용할 때는 완성된 HTML뿐 아니라 브라우저가 화면을 갱신하는 데 필요한 데이터도 조각으로 전달될 수 있습니다. 실제로 브라우저가 fallback과 완성된 내용을 별도 전송 단위로 관찰하는지는 데이터 완료 시점과 프록시·압축·브라우저 버퍼링에 따라 달라집니다.

React를 직접 Node.js HTTP 서버에 연결하는 경우에는 `renderToPipeableStream()`으로 렌더링 결과를 Node.js Writable 응답에 연결할 수 있습니다. Next.js 애플리케이션 코드에서는 이 API를 직접 호출하지 않으며, 실제 스트림 변환과 전송은 Next.js와 배포 런타임이 담당합니다.

브라우저나 네트워크가 충분히 빠르면 전송 버퍼는 곧 비워집니다. 반대로 느린 클라이언트가 많거나 중간 네트워크 구간의 전송 속도가 느리면 HTTP 응답이나 소켓의 Writable 버퍼가 차오를 수 있습니다. 이때 하위 전송 계층에서는 이 글에서 살펴본 `write()` 반환값, `drain`, `highWaterMark`와 같은 백프레셔 원리가 작동합니다. 자체 호스팅한 Node.js 런타임에서는 최종 전송 단계가 `ServerResponse`와 소켓 Writable로 이어질 수 있지만, 일반적인 Next.js 페이지 코드에서 그 객체나 `writableLength`를 직접 다루지는 않습니다.

앞에서 실행한 느린 Writable 예제에 대응해 보면 각 역할이 더 분명해집니다.

| 느린 Writable 예제  | Next.js 화면 전송에서 대응하는 대상               |
| ------------------- | ------------------------------------------------- |
| `chunk`             | React가 만든 HTML 또는 화면 데이터 조각           |
| `slowSink`          | 느린 브라우저로 이어지는 HTTP 응답과 소켓         |
| `write() === false` | 전송 계층이 지금은 데이터를 더 받기 어렵다는 신호 |
| `drain`             | 대기 데이터가 전송되어 다시 쓸 수 있게 된 시점    |

이 표는 개념의 역할을 대응한 것입니다. 일반적인 Next.js 페이지에서 `slowSink.write()`를 직접 호출한다는 뜻은 아닙니다.

따라서 증상에 따라 살펴볼 위치도 달라집니다.

| 관찰한 현상                                             | 먼저 확인할 위치                                   |
| ------------------------------------------------------- | -------------------------------------------------- |
| 초기 화면과 fallback도 늦게 나타남                      | Suspense 바깥의 데이터 요청과 서버 렌더링          |
| fallback은 빠르지만 실제 콘텐츠가 늦게 나타남           | Suspense 안쪽의 데이터 요청과 비동기 작업          |
| 서버는 조각을 만들었지만 브라우저에서 한꺼번에 나타남   | 프록시, CDN, 압축 또는 브라우저의 응답 버퍼링      |
| 느린 사용자가 많을수록 서버의 응답 대기량과 메모리 증가 | HTTP 응답 스트림, 소켓과 클라이언트 연결 종료 처리 |

`highWaterMark`를 키운다고 Suspense 안의 데이터가 더 빨리 준비되거나 화면 조각의 경계가 바뀌지는 않습니다. 반대로 Suspense 경계를 잘 나눴더라도 전송 계층이 막히면 메모리에 대기하는 데이터가 늘어날 수 있습니다. 렌더링 결과가 준비되는 시간과 네트워크 전송 대기 시간을 나누어 관찰해야 하는 이유입니다.

### 로컬에서는 무엇을 확인해야 할까요

`RelatedArticles`의 데이터 준비를 2초 정도 늦춘 개발용 페이지가 있다면 다음 순서를 눈으로 확인해 보세요.

1. 페이지 본문과 “관련 글을 불러오는 중입니다.”라는 fallback이 먼저 나타납니다.
2. 약 2초 뒤에 fallback이 실제 관련 글 목록으로 바뀝니다.
3. 브라우저 개발자 도구의 Network 패널에서 문서 요청이 시작된 시각과 화면이 바뀐 시각을 비교합니다.

개발 서버, 압축, 프록시와 브라우저의 버퍼링 방식에 따라 응답 조각이 Network 패널에서 각각 분리되어 보이지 않을 수 있습니다. 이 경우 화면이 나타나는 순서를 먼저 확인하고, 자동화 테스트에서는 `PassThrough` 같은 스트림으로 React 출력을 직접 받아 순서를 검증할 수 있습니다. 본문과 fallback을 받은 시점에는 지연된 콘텐츠가 없어야 하고, 대기 중인 작업을 해제한 뒤에는 그 콘텐츠가 추가되어야 합니다.

> [!NOTE]
> Next.js Route Handler는 Node.js와 Edge 런타임 모두 Web `Request`·`Response` API를 사용합니다. `ReadableStream` 응답을 직접 만들 때는 controller의 `desiredSize`로 소비 여유를 확인할 수 있습니다. 별도의 `WritableStream`에 쓰는 경우에는 writer의 `desiredSize`와 `ready`를 사용합니다. Edge Runtime에서는 Node.js의 `write()`와 `drain`을 직접 사용할 수 없습니다. API의 이름과 사용법은 달라도 느린 소비자에 맞춰 생산 속도를 조절해야 한다는 목적은 같습니다.

## 메모리 누수와 구분해서 보기

백프레셔 문제를 확인할 때는 다음 신호를 같은 시간축에서 살펴봅니다.

| 신호                       | 해석할 때 주의할 점                                                                                                                                      |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `writableLength`           | 특정 Writable 스트림 앞에 얼마나 대기하는지 보여줍니다. 프로세스 전체 메모리와 같지는 않습니다.                                                          |
| `write()`의 `false` 비율   | 생산자가 소비자 속도를 자주 앞서는지 보여줍니다. `false` 자체는 오류가 아닙니다.                                                                         |
| `drain`까지 걸린 시간      | 소비자가 따라잡는 데 필요한 시간을 보여줍니다. 긴 시간이 반복되면 하위 스트림을 조사해야 합니다.                                                         |
| `rss`                      | JavaScript 힙, 네이티브 할당, Buffer와 코드 등을 포함한 프로세스 메모리입니다.                                                                           |
| `heapUsed`                 | V8 힙에서 사용하는 메모리입니다. Buffer의 데이터 저장 공간 전체를 대표하지는 않습니다.                                                                   |
| `external`, `arrayBuffers` | Buffer의 데이터 저장 공간처럼 V8 힙 밖에서 관리되는 메모리 증가를 구분하는 데 도움이 됩니다. `arrayBuffers`는 `external`에도 포함되므로 더하지 않습니다. |

관측값을 원인과 연결할 때는 다음 패턴을 출발점으로 사용할 수 있습니다.

| 관측 패턴                                                     | 먼저 확인할 곳                               |
| ------------------------------------------------------------- | -------------------------------------------- |
| `writableLength`가 계속 높고 `writableNeedDrain`이 유지됨     | 느린 소비자와 `write()` 반환값을 무시한 코드 |
| `arrayBuffers`가 대기량과 함께 증가함                         | 처리되지 않은 Buffer 청크와 별도 큐          |
| 입력과 스트림 종료 뒤에도 `heapUsed` 기준선이 반복해서 상승함 | 회수되지 않는 JavaScript 객체 참조           |
| `heapTotal`은 안정적인데 RSS가 높은 수준으로 유지됨           | 네이티브 메모리와 할당자 단편화 가능성       |

RSS가 오르더라도 GC 이후의 `heapUsed`가 안정적이고 `writableLength`나 `arrayBuffers`가 처리량에 맞춰 변한다면, 전형적인 JavaScript 힙 누수와는 원인이 다를 수 있습니다. 반대로 입력을 멈추고 모든 스트림이 종료된 뒤에도 힙의 기준선이 반복 실행마다 올라간다면 별도의 참조 누수를 조사해야 합니다.

메모리 값 하나만으로 원인을 확정해서는 안 됩니다. Linux에서는 할당자 단편화 때문에 `heapTotal`이 안정적이어도 RSS가 높은 수준으로 유지될 수 있습니다. Buffer 객체의 데이터 저장 공간은 V8 힙 밖의 지표에 더 직접적으로 나타날 수도 있습니다.

## 운영에서 확인할 순서

1. `write()` 반환값을 무시하는 반복문이나 이벤트 핸들러가 있는지 찾습니다.
2. `writableLength`, `writableHighWaterMark`, `writableNeedDrain`을 문제 스트림 단위로 관찰합니다.
3. 생산자 처리량과 소비자 처리량, `drain`까지 걸린 시간을 같은 구간에서 비교합니다.
4. `rss`, `heapUsed`, `external`, `arrayBuffers`를 함께 보고 어느 메모리 영역이 증가하는지 구분합니다.
5. 수동 연결이라면 `pipeline()`으로 흐름 제어와 오류 처리를 단순화할 수 있는지 검토합니다.
6. 입력을 중단하고 스트림을 종료한 뒤 기준선이 회복되는지 확인해 지속적인 참조 누수와 구분합니다.

먼저 `write() === false`인데도 생산을 계속하는 지점이 있는지 확인해 보세요. 해당 흐름을 고친 뒤 입력을 중단했을 때 메모리 기준선이 회복되는지 확인하면 백프레셔 문제와 지속적인 누수를 한 단계 더 명확하게 구분할 수 있습니다.
