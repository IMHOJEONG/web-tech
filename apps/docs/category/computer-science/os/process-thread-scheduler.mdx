## Process와 Thread를 나누는 이유

- process는 실행 중인 프로그램의 독립된 자원 단위로 볼 수 있다.

- thread는 process 안에서 실행 흐름을 나누는 단위로 볼 수 있다.

- 두 개를 구분하면 메모리 격리, context switching, 동시성 문제를 더 명확하게 볼 수 있다.

### Process

- 기본적으로 독립된 가상 주소 공간(address space)을 가진다. 프로세스가 사용하는 주소의 범위와 매핑이 분리된다는 뜻이다.

- 다른 프로세스의 일반 변수를 자기 변수처럼 읽을 수는 없다. 다만 공유 메모리 같은 명시적인 프로세스 간 통신(IPC) 수단으로 일부 영역을 공유할 수 있다.

- 문맥 교환(context switching)은 실행을 멈춘 흐름의 상태를 저장하고 다른 흐름의 상태를 복원하는 일이다. 주소 공간 전환 여부와 캐시 상태 등도 비용에 영향을 주므로 프로세스와 스레드의 전환 비용을 고정된 배수로 비교하지 않는다.

### Thread

- 같은 프로세스의 주소 공간을 공유하지만 각 스레드는 자체 실행 상태와 스택을 가진다. 별도 스택이 있다는 것이 다른 스레드로부터 메모리 접근이 격리된다는 뜻은 아니다.

- 공유 값에 접근하는 순서에 따라 결과가 달라지는 경쟁 조건(race condition)에 주의해야 한다. 잠금이나 원자적 연산 등 상황에 맞는 동기화가 필요하다.

- 동시 실행 흐름을 만들 때 더 가볍게 사용할 수 있다.

### Scheduler

- scheduler는 어떤 실행 흐름에 CPU 시간을 줄지 결정한다.

- 목표는 공정성, 응답성, 처리량 사이에서 균형을 잡는 것이다.

- 사용자 입력에 빠르게 반응해야 하는 작업과 대량 계산을 처리하는 작업은 좋은 스케줄링 기준이 다를 수 있다.

### 같은 카운터를 올린다면

두 프로세스가 각각 일반 변수 `count = 0`을 가진 경우, 한쪽의 값을 바꿨다고 다른 쪽의 변수까지 바뀌지는 않는다. 반면 두 프로세스가 같은 공유 메모리 영역을 매핑하면 그 영역의 데이터를 주고받을 수 있다. 각자 독립된 주소 공간을 갖는 것과 일부 메모리를 공유하는 것은 모순이 아니다.

같은 프로세스의 두 스레드가 공유 카운터를 각각 읽고 1을 더한 뒤 저장한다고 가정해 보자. 둘 다 0을 읽은 뒤 각각 1을 저장하면 두 번 증가시켰어도 결과는 1일 수 있다. 공유 메모리를 쓰는 두 프로세스에도 같은 동기화 문제가 생길 수 있다. 이 예는 가능한 실행 순서를 설명한 것이며 특정 OS에서 실행해 측정한 결과는 아니다.

## 실무 연결

- Node.js 서버에서 CPU 작업이 길어지면 event loop가 밀린다.

- 브라우저에서 main thread가 막히면 입력과 렌더링이 늦어진다.

- 운영체제 개념은 프론트엔드와 백엔드 성능 문제를 해석하는 공통 언어가 된다.
