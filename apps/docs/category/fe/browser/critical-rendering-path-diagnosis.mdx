## 화면이 늦게 뜨면 어디부터 봐야 할까

페이지가 천천히 나타나면 번들 크기나 이미지 용량부터 의심하기 쉽다. 하지만 사용자가 기다린 시간이 서버 응답에 쓰였는지, 중요한 리소스를 늦게 발견한 것인지, main thread가 다른 작업에 붙잡힌 것인지는 기록을 보기 전까지 알 수 없다.

먼저 브라우저가 HTML을 받은 뒤 어떤 일을 거쳐 픽셀을 만드는지 살펴보자. 최적화 방법은 그다음에 골라도 늦지 않다.

## 픽셀 하나가 나타나기 전에

브라우저가 문서를 받았다고 바로 화면을 그릴 수 있는 것은 아니다. 초기 화면을 만들기까지 다음 작업이 연결된다.

1. HTML을 파싱해 DOM을 만든다.
2. CSS를 파싱해 CSSOM을 만든다.
3. 필요한 JavaScript가 DOM이나 CSSOM을 변경한다.
4. DOM과 CSSOM에서 실제로 그릴 노드를 추려 render tree를 만든다.
5. 각 노드의 크기와 위치를 계산하는 layout을 수행한다.
6. 색상, 글자, 테두리 같은 시각 정보를 paint record로 만든다.
7. 필요한 레이어를 합성해 화면에 표시한다.

이 순서는 개념 모델이다. 브라우저는 HTML을 스트리밍하며 처리하고, 주 parser가 멈춘 동안에도 preload scanner가 뒤쪽 리소스를 먼저 발견할 수 있다. 모든 단계가 문서 전체를 대상으로 정확히 한 번씩 실행된다고 이해하면 실제 trace를 잘못 읽게 된다.

> [!NOTE]
> Critical Rendering Path는 초기 화면이 그려지기까지의 의존 관계를 설명한다. 이후 DOM이나 style이 바뀌면 style calculation, layout, paint, composite 일부가 다시 실행될 수 있다.

## 기다려야 하는 것과 나중에 와도 되는 것

HTML 안에서 발견되는 모든 리소스가 같은 중요도를 갖지는 않는다.

| 리소스                                 | 초기 화면에 주는 기본 영향      | 먼저 확인할 것                                             |
| -------------------------------------- | ------------------------------- | ---------------------------------------------------------- |
| HTML                                   | DOM 구성의 시작점               | 첫 byte뿐 아니라 document 응답이 언제 끝나는가             |
| `<head>`의 적용 가능한 CSS             | 기본적으로 render-blocking      | 현재 viewport에 필요하지 않은 CSS까지 기다리는가           |
| `async`, `defer`가 없는 classic script | 기본적으로 parser-blocking      | 앞선 stylesheet와 script 다운로드·실행이 parser를 멈추는가 |
| 이미지                                 | 보통 HTML parsing을 막지 않음   | LCP 후보가 늦게 발견되거나 크기가 예약되지 않았는가        |
| 웹 폰트                                | text 표시와 layout shift에 영향 | `font-display`, fallback metric, 발견 시점이 적절한가      |

`async`, `defer`, preload를 붙이는 것 자체가 목표는 아니다. `defer`와 module script는 parsing이 끝난 뒤 실행되지만 실행 시점의 긴 작업은 여전히 rendering 기회를 밀 수 있고, `async` script도 실행되는 순간에는 main thread와 경쟁한다. 언제 발견하고 언제 실행해야 하는지를 먼저 정한다.

## LCP 하나를 네 구간으로 쪼개기

LCP는 paint 함수가 실행된 시간만 측정하지 않는다. navigation을 시작한 순간부터 viewport 안의 가장 큰 image 또는 text block이 그려질 때까지의 결과다. 원인을 찾으려면 전체 시간을 네 구간으로 나눈다.

| 구간                   | 의미                                      | trace에서 확인할 것                                       |
| ---------------------- | ----------------------------------------- | --------------------------------------------------------- |
| TTFB                   | navigation 시작부터 HTML 첫 byte까지      | redirect, DNS, connection, request waiting, server timing |
| Resource load delay    | TTFB부터 LCP resource 요청 시작까지       | HTML에서의 발견 위치, client rendering, preload 여부      |
| Resource load duration | LCP resource 다운로드 시간                | 크기, 우선순위, bandwidth 경쟁, cache                     |
| Element render delay   | resource 완료부터 element가 그려질 때까지 | CSS 차단, decode, font, JavaScript, main-thread 작업      |

예를 들어 이미지를 더 작게 만들어 load duration을 줄여도, JavaScript가 element를 계속 숨기고 있다면 절약한 시간이 render delay로 옮겨갈 수 있다. 숫자 하나보다 어느 구간이 길어졌는지를 봐야 하는 이유다.

text block이 LCP라면 별도의 LCP image request가 없으므로 resource load delay와 duration은 0일 수 있다. 이때는 font와 render-blocking CSS, main-thread 작업을 중심으로 element render delay를 살펴본다.

## 서로 다른 지표를 하나의 문제로 묶지 않기

- LCP는 page load 중 주요 콘텐츠가 언제 보였는지를 설명한다.
- CLS는 viewport에서 발생한 예기치 않은 layout shift를 session window로 묶고, 최대 5초인 window 중 점수 합계가 가장 큰 구간을 보고한다.
- INP는 interaction의 `input delay`, event callback의 `processing duration`, 다음 frame까지의 `presentation delay`를 포함한다.

INP가 느리다고 해서 click handler만 긴 것은 아니다. 입력 전에 실행 중이던 long task가 event 전달을 늦출 수도 있다. 반대로 초기 화면 trace만 기록해서는 페이지 생명주기 전반의 interaction을 대표하는 INP를 충분히 재현할 수 없다.

## 현장 데이터에서 실험실 기록으로

한 번의 DevTools 기록은 특정 device, network, cache, viewport에서 얻은 표본이다. 먼저 CrUX나 RUM에서 실제 사용자의 URL·기기별 분포를 확인하고, 문제가 큰 조건을 local lab에서 재현한다.

재현할 때는 다음 조건을 기록한다.

- Chrome version, viewport와 device scale factor
- CPU와 network throttling
- cold cache와 warm cache 여부
- 로그인 상태, route와 query
- extension 영향을 줄이기 위한 별도 profile 또는 Incognito 사용 여부

같은 조건에서도 background process와 scheduler의 영향으로 값이 달라질 수 있다. 변경 전후를 한 번씩만 비교하지 말고 여러 번 기록해 대표적인 trace와 분포를 비교한다.

## 네 가지 페이지로 직접 확인하기

이 저장소에는 의존성 없이 실행할 수 있는 작은 실험 서버가 있다.

```bash
pnpm dev:crp-lab
```

서버는 `127.0.0.1:4173`에서 다음 페이지를 제공한다.

| 페이지             | 바꾼 조건                        | 확인할 가설                                               |
| ------------------ | -------------------------------- | --------------------------------------------------------- |
| `/baseline`        | 의도적인 지연 없음               | 비교 기준 trace를 만든다                                  |
| `/slow-css`        | stylesheet 응답을 1.2초 지연     | render-blocking CSS가 첫 화면을 미루는가                  |
| `/blocking-script` | classic script 응답을 1.2초 지연 | parser가 멈추고 preload scanner가 뒤쪽 image를 발견하는가 |
| `/late-lcp`        | hero image를 1.2초 뒤 DOM에 추가 | LCP resource load delay가 어떻게 달라지는가               |

실험 장치의 기본 동작과 Chromium에서 관측되는 event 순서는 자동 테스트로도 확인할 수 있다.

```bash
pnpm test:crp-lab
pnpm test:crp-lab:browser
```

브라우저 테스트는 특정 FCP·LCP 수치를 정답으로 고정하지 않는다. CSS 응답과 FCP, parser-blocking script와 `DOMContentLoaded`, baseline과 늦게 발견한 hero request 사이의 순서를 비교한다. 실제 성능 수치는 아래 절차대로 여러 번 기록해 해석한다.

### 같은 조건으로 기록하기

1. DevTools의 Network에서 `Disable cache`를 켠다.
2. Performance panel에서 Screenshots를 켜고 새로고침 recording을 시작한다.
3. LCP marker와 Insights의 `LCP by phase`, `LCP request discovery`를 확인한다.
4. Network track에서 stylesheet, script, hero image의 요청 시작 시점을 비교한다.
5. Main track에서 Parse HTML과 script evaluation, style/layout/paint 순서를 연결한다.
6. 각 mode를 최소 세 번 기록하고 아래 표에 결과를 남긴다.

| Mode            | FCP | LCP | TTFB | Load delay | Load duration | Render delay | 관찰 |
| --------------- | --- | --- | ---- | ---------- | ------------- | ------------ | ---- |
| baseline        |     |     |      |            |               |              |      |
| slow-css        |     |     |      |            |               |              |      |
| blocking-script |     |     |      |            |               |              |      |
| late-lcp        |     |     |      |            |               |              |      |

> [!TIP]
> 지연 시간은 정답을 만들기 위한 값이 아니다. local machine과 Chrome 상태에 따라 결과가 달라지므로 숫자 자체보다 waterfall과 main-thread event의 순서를 설명해본다.

### 한 번에 하나만 바꾸기

CSS 분리, image preload, JavaScript defer를 동시에 적용하면 어떤 변경이 효과가 있었는지 알 수 없다. 실험 mode 하나를 기준으로 병목 가설 하나만 바꾸고, 같은 조건에서 다시 기록한다.

## TTFB가 길다고 서버 코드부터 열지 않기

navigation TTFB에는 redirect, service worker startup, DNS, TCP/TLS connection, request latency와 server waiting이 함께 들어갈 수 있다. Network의 Timing 탭과 `Server-Timing` header를 함께 보고 소유 구간을 좁힌다.

TTFB가 짧아도 HTML streaming이 오래 걸리면 document 완료와 뒤쪽 resource 발견이 늦을 수 있다. 첫 byte와 `responseEnd`를 구분해서 본다.

## 최적화가 오히려 멀어지는 순간

- Lighthouse 한 번의 점수만 보고 실제 사용자의 느린 구간을 단정한다.
- 모든 image와 font를 preload해 bandwidth 경쟁을 만든다.
- animation이 끊긴다는 이유만으로 무조건 `will-change`를 추가한다.
- LCP resource 크기만 줄이고 discovery와 render delay는 확인하지 않는다.
- 개발 환경의 React 검사 도구와 source map 비용을 production 성능으로 해석한다.
- trace를 남기지 않고 여러 최적화를 한꺼번에 적용한다.

## 기록을 닫기 전에

- 현장 데이터에서 어떤 사용자 조건이 느린지 확인했는가?
- LCP element가 image인지 text인지 확인했는가?
- LCP의 네 구간 중 어디에서 시간이 늘어났는가?
- 첫 화면에 필요하지 않은 CSS나 classic script가 경로를 막고 있지 않은가?
- image와 embed 영역의 크기를 미리 예약했는가?
- cold cache와 warm cache를 구분했는가?
- 변경 전후를 여러 번 같은 조건으로 기록했는가?
- trace와 결론을 다른 사람이 재현할 수 있게 남겼는가?
