## 경계를 먼저 정해야 하는 이유

- 서버 컴포넌트와 클라이언트 컴포넌트는 실행 위치가 다르다.

- 경계가 흐려지면 데이터 fetch, bundle size, interaction 책임이 한 컴포넌트에 섞인다.

- 컴포넌트가 어디서 실행되는지보다 어떤 책임을 갖는지가 더 중요하다.

### 서버 컴포넌트에 어울리는 것

- 데이터 조회

- 인증 상태에 따른 서버 판단

- markdown, HTML, CMS payload 같은 서버 전용 데이터 조합

- interaction이 없는 레이아웃과 정적 콘텐츠

### 클라이언트 컴포넌트에 어울리는 것

- 사용자 입력 처리

- 클릭, 드래그, 키보드 이벤트

- local state와 browser API 사용

- animation과 optimistic UI

### 경계가 잘못 잡혔다는 신호

- 단순 데이터 표시 컴포넌트에 `use client`가 붙어 있다.

- 서버에서만 필요한 token이나 env가 client boundary 근처로 밀려난다.

- 작은 버튼 하나 때문에 큰 페이지 전체가 client component가 된다.

## 판단 기준

- “이 컴포넌트가 브라우저 이벤트를 직접 다루는가?”를 먼저 묻는다.

- 이벤트가 없다면 서버 컴포넌트로 시작하고, interaction이 필요한 가장 작은 지점에서 client boundary를 둔다.

- 서버에서 가져온 데이터는 직렬화 가능한 props로 클라이언트에 넘긴다.

> [!TIP]
> 판단이 애매하다면 서버 컴포넌트로 시작하고, 실제 브라우저 이벤트가 필요한 가장 작은 컴포넌트에만 `use client`를 붙이는 편이 안전하다.
