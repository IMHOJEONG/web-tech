## Next.js 패키지를 살펴보는 이유

이 글은 패키지 내부를 분석한 결과 보고서가 아니라, 오류가 발생했을 때 어디부터 살펴볼지 정리한 체크리스트다. 설치 버전과 재현 환경을 먼저 고정하고 내부 구현은 그 버전에 한정해서 읽는다.

- 프레임워크를 사용할 때는 공개 API만 알아도 기능을 만들 수 있다.

- 다만 빌드 결과, 서버 렌더링, 라우팅 동작을 디버깅하려면 패키지 내부 구조를 어느 정도 이해하는 편이 좋다.

- 특히 Next.js는 React, 번들러, 서버 런타임이 맞물려 있어서 문제가 생겼을 때 원인을 한 계층에서만 찾기 어렵다.

### 먼저 확인할 영역

앱 디렉터리에서 `node -p "require('next/package.json').version"`으로 실제 설치 버전을 확인한다. 모노레포 루트와 앱이 서로 다른 의존성을 해석할 수 있으므로 오류가 난 앱 위치에서 실행한다.

- 에러가 `next dev`, `next build`, `next start` 중 어느 명령에서 발생했는지 적는다.
- 재현 라우트, App Router/Pages Router 여부, Node.js 버전, 첫 번째 오류 메시지를 함께 기록한다. 개인정보나 인증값은 남기지 않는다.

- `next` 패키지가 앱 라우터와 페이지 라우터를 어떻게 나누어 제공하는지 본다.

- 서버 렌더링 템플릿과 런타임 코드가 빌드 결과에 어떤 형태로 포함되는지 확인한다.

- 개발 서버와 프로덕션 빌드에서 사용하는 모듈 로딩 방식이 어떻게 달라지는지 비교한다.

## 읽을 때의 기준

- 내부 구현을 외워두기보다, 에러 메시지가 어느 계층에서 발생했는지 추적할 수 있는 정도를 목표로 둔다.

- 문서화된 API와 내부 파일 경계를 구분해서, 내부 구조에 직접 의존하는 코드는 만들지 않는다.

확인 기록에는 "관찰한 사실 → 원인 가설 → 비교 방법 → 실제 결과"를 나눠 적는다. 아직 실행하지 않은 내부 분석이나 수정 효과를 결과처럼 작성하지 않는다.
