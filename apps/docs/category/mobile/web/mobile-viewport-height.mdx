## 휴대전화에서는 화면 높이가 하나가 아닙니다

처음 접속한 화면에서는 하단 버튼이 잘리지 않다가, 주소창이 나타나면 버튼이 아래로 밀리는 경우가 있습니다. 화면을 가득 채우려고 `height: 100vh`를 넣었는데 오히려 스크롤이 생기기도 합니다. 데스크톱에서 브라우저 폭을 좁혀 볼 때는 잘 보이던 화면이라 더 헷갈립니다.

모바일에서는 웹페이지 외에 주소창과 탭 표시줄도 화면을 차지합니다. 이 도구들이 접히고 펼쳐지면 **지금 내용을 볼 수 있는 높이**도 바뀝니다. CSS에서 어느 높이를 기준으로 삼을지 먼저 정해야 합니다.

여기서 <strong>뷰포트(viewport)</strong>는 웹페이지를 표시하는 창의 영역입니다. 휴대전화의 물리적인 해상도와 같은 뜻은 아닙니다. CSS 픽셀도 화면의 물리 픽셀과 일대일로 대응한다고 가정하지 않습니다. 기기 해상도 숫자를 그대로 가져와 페이지 높이에 쓰면 안 되는 이유입니다.

## vh·svh·lvh·dvh가 바라보는 높이

`1vh`는 기준 높이의 1%입니다. 중요한 부분은 그 **기준**입니다. 현재 CSS 명세에서 `vh`는 `lvh`와 같은 큰 뷰포트를 기준으로 합니다. 주소창 등이 접혀 공간이 넓어진 상태를 생각하시면 됩니다. 따라서 `100vh`가 주소창이 펼쳐진 순간의 보이는 높이와 항상 같지는 않습니다. [CSS Values and Units 명세](https://drafts.csswg.org/css-values-4/#viewport-relative-lengths)

| 단위  | 기준이 되는 높이                                | 화면을 설계할 때 고려할 점                                                   |
| ----- | ----------------------------------------------- | ---------------------------------------------------------------------------- |
| `svh` | 주소창 등 동적 브라우저 UI가 펼쳐진 작은 뷰포트 | 주소창이 접혀도 높이가 안정적이며, 아래쪽에 여유 공간이 남을 수 있습니다.    |
| `lvh` | 해당 UI가 접힌 큰 뷰포트                        | 넓은 공간을 채우지만 UI가 펼쳐지면 내용이 가려질 수 있습니다.                |
| `dvh` | 해당 UI 상태를 반영하는 동적 뷰포트             | 보이는 공간에 맞춰 크기가 달라지므로 스크롤 중 내용 배치도 변할 수 있습니다. |
| `vh`  | 큰 뷰포트, 즉 `lvh`와 같은 기준                 | 모바일에서 늘 현재 보이는 높이라고 해석하면 안 됩니다.                       |

이해를 위한 가상의 예로, 주소창이 펼쳐졌을 때의 기준 높이가 700px이고 접혔을 때 800px이라면 `100svh`는 700px, `100lvh`와 `100vh`는 800px입니다. `100dvh`는 해당 UI 상태에 따라 달라집니다. 이 숫자는 실제 기기를 측정한 값이 아닙니다.

`svh`가 모든 상황에서 고정된 픽셀값이라는 뜻은 아닙니다. 화면을 회전하거나 창 자체의 크기를 바꾸면 기준도 달라집니다. 주소창의 접힘만으로 높이를 계속 바꾸지 않는다는 의미입니다. [MDN 길이 단위 설명](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length)

시작 화면이나 짧은 안내 페이지라면 `svh`로 높이를 안정시키는 선택이 가능합니다. 채팅 화면처럼 남는 공간을 계속 활용해야 하는 UI에서는 `dvh`가 후보가 됩니다. 다만 주소창 애니메이션의 모든 프레임에 맞춰 높이가 부드럽게 바뀐다는 보장은 없습니다. 사용 중 크기 변경이 내용과 버튼을 움직이는지도 함께 보셔야 합니다. [web.dev의 뷰포트 단위 설명](https://web.dev/blog/viewport-units)

## 짧은 내용은 채우고 긴 내용은 늘어나도록 만듭니다

안내 문구와 버튼이 있는 화면을 만들어 보겠습니다. 예제의 목표는 버튼의 위치와 문서의 높이를 확인하는 것입니다. 버튼에 페이지 이동 기능은 연결하지 않습니다.

먼저 다음 내용을 `viewport.html`로 저장합니다. `viewport.css`는 같은 폴더에 둡니다. `width=device-width`는 모바일의 CSS 레이아웃 폭을 기기에 맞추는 설정이며, `initial-scale=1`은 초기 확대 배율을 지정합니다. `viewport-fit=cover`는 화면의 안전 영역까지 배경을 확장하는 레이아웃에 사용합니다. 확대를 막는 `user-scalable=no`는 넣지 않았습니다. [MDN viewport 메타 설명](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)

```html filename="viewport.html" part="1/1"
<!doctype html>
<html lang="ko">
    <head>
        <meta charset="utf-8" />
        <meta
            name="viewport"
            content="width=device-width, initial-scale=1, viewport-fit=cover"
        />
        <title>모바일 화면 높이 살펴보기</title>
        <link rel="stylesheet" href="viewport.css" />
    </head>
    <body>
        <main class="screen">
            <h1>오늘의 기록을 시작합니다</h1>
            <p>글이 길어지면 화면도 아래로 늘어날 수 있습니다.</p>
            <button type="button">계속하기</button>
        </main>
    </body>
</html>
```

CSS에서는 `height` 대신 <strong><code>min-height</code></strong>를 사용합니다. 최소 높이만 정해 두면 내용이 짧을 때는 화면을 채우고, 글이 많거나 글자 크기를 키웠을 때는 내용에 맞춰 늘어납니다. 정해진 한 화면 안에 반드시 모든 내용을 넣으려다가 문구를 자르는 일을 피할 수 있습니다.

```css filename="viewport.css" part="1/2"
body {
    margin: 0;
    font-family: system-ui, sans-serif;
    line-height: 1.6;
}

.screen {
    box-sizing: border-box;
    min-height: 100vh;
    min-height: 100svh;
    display: flex;
    flex-direction: column;
    gap: 1rem;
    padding-top: calc(1rem + env(safe-area-inset-top, 0px));
    padding-right: calc(1rem + env(safe-area-inset-right, 0px));
    padding-bottom: calc(1rem + env(safe-area-inset-bottom, 0px));
    padding-left: calc(1rem + env(safe-area-inset-left, 0px));
}
```

같은 파일에 아래 내용을 이어 붙입니다. 제목과 문단의 기본 바깥 여백을 없애고, 버튼 위에 남는 공간을 배분합니다.

```css filename="viewport.css" part="2/2"
.screen h1,
.screen p {
    margin: 0;
}

.screen button {
    margin-top: auto;
    align-self: flex-start;
    font: inherit;
    padding: 0.75rem 1rem;
}
```

동일한 속성을 두 번 쓴 것은 순서가 있는 대체 처리입니다. `svh`를 이해하는 브라우저에서는 뒤의 선언이 적용되고, 이해하지 못하면 앞의 `100vh`가 남습니다. 오래된 브라우저에서도 주소창 가림까지 해결된다는 보장은 없으므로 지원 대상 기기에서 확인해야 합니다.

`box-sizing: border-box`는 최소 높이 계산에 패딩과 테두리를 포함하도록 합니다. 이 설정이 없으면 높이 위에 패딩이 더해져, 한 화면을 채우려던 요소가 더 커질 수 있습니다. 버튼의 `margin-top: auto`는 세로 방향으로 남는 공간을 위쪽 여백에 배분합니다. 내용이 길어지면 버튼도 문서 흐름에 따라 아래로 이동합니다.

두 번째 `min-height`의 단위를 `100dvh`로 바꾸면 주소창 상태를 반영하는 쪽을 비교할 수 있습니다. 단위만 바꿔도 충분한지, 하단 버튼이 스크롤 중 계속 움직이지는 않는지 직접 확인해 보시면 좋습니다.

두 파일을 저장한 폴더에서 Python 3을 사용할 수 있다면 `python3 -m http.server 8080 --bind 127.0.0.1`을 실행한 뒤 `http://127.0.0.1:8080/viewport.html`을 여세요. 이 명령은 같은 컴퓨터에서 확인하는 용도입니다. 실기기 확인에는 휴대전화에서 접근 가능한 테스트 주소가 필요합니다. 같은 폴더에 HTML과 CSS가 있어야 스타일이 적용됩니다.

## 예제에서 확인한 결과

2026년 11월 2일 데스크톱 Chromium 브라우저의 화면 영역을 390×844 CSS 픽셀로 설정해 예제를 열었습니다. 이 환경에서 `.screen`의 최소 높이는 844px, 버튼 아래쪽 위치는 828px이었고 가로 넘침은 없었습니다. CSS의 루트 `font-size`를 `200%`로 바꾼 별도 조건도 가로 넘침 없이 표시됐습니다. 이 조건은 운영체제의 글자 크기 설정이나 브라우저 확대를 재현한 것은 아닙니다.

본문 문장을 길게 늘린 별도 조건에서는 문서 높이가 약 4,110px로 늘어나고 버튼이 긴 글 아래로 내려갔습니다. `min-height`가 내용을 한 화면에 자르지 않고 늘어날 여지를 남기는 것을 확인한 결과입니다. 동적 주소창이 없는 데스크톱에서는 세 뷰포트 기준이 같은 값이 될 수 있으므로, 이 결과가 `svh`와 `dvh`의 차이를 입증하지는 않습니다. 이 검사는 모바일 주소창·화면 키보드·안전 영역이 있는 실기기를 재현한 검사가 아닙니다. 해당 동작은 지원할 기기에서 추가로 확인해야 합니다.

추가로 320×568, 390×844, 844×390 화면에서 기본 내용·긴 내용·CSS 글자 확대의 아홉 조합을 확인했습니다. 모두 가로 넘침 없이 버튼까지 이동할 수 있었습니다. 320px 폭에서 글자를 확대한 조건은 문서가 약 692px로 늘어났습니다. 높이를 억지로 한 화면에 맞추기보다 세로 스크롤을 허용해야 하는 사례입니다.

## 안전 영역은 주소창 높이와 다릅니다

<strong>안전 영역(safe area)</strong>은 카메라가 들어간 화면의 잘린 부분이나
둥근 모서리, 시스템 표시 영역 때문에 중요한 내용을 붙이지 않도록 확보하는
여유입니다. `env(safe-area-inset-bottom, 0px)`는 브라우저가 제공하는 아래쪽 안전
여백을 읽습니다. 값이 `0px`인 환경도 정상입니다. [MDN env()
설명](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env)

위 예제는 기본 여백 `1rem`에 안전 여백을 더합니다. 화면 가장자리까지 배경을 채우더라도 글자와 버튼은 안쪽으로 들어오게 합니다. 세로 화면에서는 위아래가 중요해 보여도 가로 회전 시에는 좌우 잘림도 살펴봐야 하므로 네 방향을 모두 작성했습니다.

안전 영역을 추가했다고 주소창에 따른 높이 선택이 해결되는 것은 아닙니다. 반대로 `dvh`를 사용했다고 버튼에 필요한 안전 여백이 자동으로 생기는 것도 아닙니다. **요소의 최소 높이**와 **내용을 가장자리에서 띄우는 패딩**을 각각 결정해야 합니다.

## 키보드를 열면 별도의 확인이 필요합니다

입력창을 누르면 화면 키보드가 나타납니다. 이때 `100dvh`가 언제나 키보드 위쪽 높이로 줄어든다고 생각하기 쉽지만, 그렇게 가정하면 입력 버튼이 가려질 수 있습니다. 명세는 키보드처럼 내용을 덮는 UI가 뷰포트 단위를 바꾸지 않을 수 있도록 설명합니다. 브라우저와 설정에 따라 다르게 동작하는 부분입니다. [CSS 명세의 동적 UI 설명](https://drafts.csswg.org/css-values-4/#viewport-relative-lengths)

여기서는 두 영역을 구분하면 도움이 됩니다. **레이아웃 뷰포트**는 페이지를 배치하는 기준이며, <strong>시각적 뷰포트(visual viewport)</strong>는 사용자가 현재 볼 수 있는 부분입니다. 화면을 확대하거나 키보드를 열 때 시각적 뷰포트만 작아지는 경우가 있습니다. CSS의 전체 배치 높이가 그대로여도 실제로 보이는 공간은 줄어들 수 있습니다. [MDN VisualViewport 설명](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport)

지원하는 환경에서 viewport 메타의 `interactive-widget=resizes-content` 설정은 키보드에 맞춰 레이아웃 뷰포트와 시각적 뷰포트를 함께 줄이는 동작을 지정합니다. 모든 브라우저와 WebView에 똑같이 적용되는 해결책으로 사용하면 안 됩니다. 브라우저의 기본 동작과 호환성을 먼저 확인하고, 채팅 입력창처럼 필요한 경우에만 시각적 뷰포트 API나 키보드 대응 방식을 추가로 검토하시면 됩니다. [CSS Viewport의 편집 중 명세](https://drafts.csswg.org/css-viewport/#interactive-widget-section)와 [Chrome의 키보드·뷰포트 동작 설명](https://developer.chrome.com/blog/viewport-resize-behavior)

이 글의 예제에는 입력창과 키보드 처리 코드를 넣지 않았습니다. 시작 화면의 최소 높이와 안전 여백을 확인하는 예제를 그대로 로그인 폼이나 채팅 화면의 완성된 레이아웃으로 사용하지는 마세요.

## 화면 폭을 좁히는 것만으로는 부족합니다

데스크톱의 기기 모드는 줄바꿈과 가로 넘침을 확인하는 데 유용합니다. 하지만 모바일 주소창의 실제 접힘, 홈 표시줄, 화면 키보드까지 같은 방식으로 재현한다고 볼 수는 없습니다. `svh`, `lvh`, `dvh`가 데스크톱에서 같은 값으로 계산되더라도 단위 선택이 틀렸다는 뜻은 아닙니다.

실제 기기에서는 첫 진입과 아래로 스크롤한 상태를 비교하고, 주소창을 다시 펼쳐 봅니다. 가로 회전과 글자 확대도 함께 확인합니다. 폼이 있는 화면은 키보드가 열린 상태에서 입력 내용과 제출 버튼에 접근할 수 있는지 따로 봐야 합니다. 긴 안내문을 넣었을 때 페이지가 자연스럽게 스크롤되는지도 중요합니다.

## 정리

모바일 높이 문제를 만났다면 CSS 숫자를 먼저 줄이기보다, 어느 영역이 줄어들었는지부터 보시면 원인을 좁히기 쉽습니다. 주소창 상태에 맞는 높이 단위를 고르고, 내용이 늘어날 여지를 남기고, 안전 영역과 키보드는 별도로 확인하는 순서입니다.
