## 이벤트 루프를 보는 이유

브라우저 메인 스레드에서는 현재 실행 중인 JavaScript와 사용자 입력 처리, 화면 갱신을 위한 작업이 실행 기회를 나눠 쓴다. 이 글은 함수와 콜백에 익숙한 개발자를 위한 노트로, 먼저 브라우저의 실행 순서를 살펴본다. Worker처럼 별도로 실행되는 환경까지 하나의 호출 스택으로 묶는 설명은 아니다.

이벤트 루프는 준비된 작업을 언제 실행할지 이해하는 기준이다. 성능 문제에서는 작업이 어느 큐에 있는지뿐 아니라, 지금 실행 중인 작업이 얼마나 오래 다른 작업을 기다리게 하는지도 확인해야 한다.

### 기본 용어와 처리 규칙

- 호출 스택(call stack): 현재 실행 중인 함수 호출을 관리한다. 동기 코드는 실행 도중에 microtask 때문에 끊기지 않는다.
- task: 타이머 콜백이나 사용자 입력 처리 등 실행할 작업의 단위다. 서로 다른 출처의 task 전체가 하나의 FIFO 큐에 들어간다고 단순화하지 않는다.
- microtask: Promise 반응 콜백이나 `queueMicrotask()`로 예약하는 작업이다. 현재 동기 코드에 끼어드는 작업은 아니다.

브라우저는 **microtask checkpoint에서 큐가 빌 때까지 microtask를 처리한다.** 처리 중 새로 예약한 microtask도 같은 checkpoint에서 이어서 처리한다. 이는 "먼저 실행되는 경향"이 아니라 정해진 처리 규칙이다.

task가 끝난 뒤가 대표적인 checkpoint지만, 그것이 유일한 지점은 아니다. 따라서 "모든 task보다 microtask가 무조건 먼저 실행된다"가 아니라, 언제 checkpoint에 도달하는지 구분해서 읽어야 한다.

### 실행 순서를 직접 확인하기

아래 코드를 브라우저 DevTools의 Sources → Snippets에서 한 번에 실행한다. 줄별로 따로 실행하지 않는다. 콘솔에서 실행한다면 개발자 도구가 자체 표시하는 반환값과 이 코드의 로그를 구분한다.

```js
;(() => {
    console.log('sync:start')

    setTimeout(() => console.log('task:timer'), 0)

    Promise.resolve().then(() => {
        console.log('microtask:promise')
        queueMicrotask(() => console.log('microtask:nested'))
    })

    queueMicrotask(() => console.log('microtask:queued'))
    console.log('sync:end')
})()
```

이 코드의 예상 출력은 다음과 같다.

```text
sync:start
sync:end
microtask:promise
microtask:queued
microtask:nested
task:timer
```

1. 두 동기 로그가 먼저 출력된다. `setTimeout(..., 0)`도 현재 실행 중인 코드를 중단하지 않으며, 정확히 0ms 뒤 실행된다는 뜻이 아니다.
2. 이미 이행된 Promise의 `then` 콜백이 먼저 예약되고, 다음으로 `queueMicrotask` 콜백이 예약된다. Promise가 항상 더 높은 우선순위를 갖는다는 뜻은 아니다.
3. Promise 콜백에서 예약한 `nested`는 이미 기다리는 `queued` 뒤에 추가된다. 큐가 빌 때까지 처리하므로 `nested`도 타이머보다 먼저 출력된다.
4. 이 예제의 microtask 처리가 끝난 후 타이머 콜백이 실행된다.

### 실행 순서와 화면 갱신은 다르다

microtask가 스스로 다음 microtask를 계속 만들면 checkpoint가 길어져 다음 task나 렌더링 기회를 지연시킬 수 있다. `Promise.resolve().then(...)`로 무거운 계산을 옮겼다고 메인 스레드를 다른 작업에 양보한 것은 아니다.

위 로그만으로 타이머 전에 화면이 반드시 한 번 그려졌다고 결론 낼 수는 없다. 실제 렌더링 여부는 브라우저의 렌더링 기회와 문서 상태 등에도 영향을 받는다. 이 예제는 콜백 순서만 확인하며 paint 시점이나 지연 시간을 측정하지 않는다.

### 브라우저에서 확인할 것

- 긴 JavaScript task가 main thread를 오래 점유하는지 확인한다.

- promise callback이 연속으로 쌓여 렌더링 기회를 빼앗는지 확인한다.

- input, scroll, animation이 같은 main thread 자원을 공유한다는 점을 고려한다.

### Node.js에서 확인할 것

앞 예제는 브라우저 기준이다. Node.js의 I/O 단계, `process.nextTick()`, CommonJS/ES module 실행 맥락까지 이 결과로 일반화하지 않는다. 여기서는 서버 성능을 볼 때의 확인 항목만 정리한다.

- I/O callback과 timer callback이 어느 단계에서 실행되는지 확인한다.

- CPU 작업이 길어지면 비동기 I/O 자체가 빨라져도 응답은 지연될 수 있다.

- event loop lag는 이벤트 루프가 작업을 처리할 기회가 늦어지는 정도를 나타내는 지표다. API 전체 응답 시간과 함께 보되 같은 값으로 취급하지 않는다.

## 실무 체크리스트

- 긴 반복문이나 큰 JSON 처리처럼 main thread를 오래 막는 작업이 있는가?

- microtask를 재귀적으로 계속 만드는 코드가 있는가?

- 사용자 입력 직후 실행되는 로직이 화면 업데이트보다 먼저 몰려 있지는 않은가?

- 서버에서는 event loop lag와 API latency를 함께 보고 있는가?
