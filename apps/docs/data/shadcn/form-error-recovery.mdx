## 저장을 눌렀는데 무엇을 고쳐야 할지 모를 때

가입 폼에 정보를 입력하고 버튼을 눌렀습니다. 화면 위에 “입력값이 올바르지 않습니다”라는 문구만 나타납니다. 이메일이 문제인지, 비밀번호가 짧은지 알 수 없습니다. 몇 번 고친 뒤에도 실패하면 사용자는 자신이 잘못 입력했다고 생각하거나 폼을 떠납니다.

오류가 발생하는 일 자체를 모두 없애기는 어렵습니다. 대신 사용자가 **어느 입력란을 어떻게 고치면 되는지** 찾는 시간을 줄일 수 있습니다. 이 글에서는 이메일 입력란 하나로 그 과정을 만들어 봅니다. 컴포넌트 라이브러리를 쓰는 경우에도 같은 질문을 적용할 수 있습니다. 오류 문구가 보이는지에 이어, 입력란과 연결되는지, 키보드로 돌아갈 수 있는지까지 확인하는 것입니다.

## 오류가 나기 전부터 안내를 나눕니다

입력란에는 이름, 사전 안내, 오류 설명이 서로 다른 역할로 필요합니다. 이름인 `label`은 무엇을 입력하는 곳인지 알려 줍니다. 사전 안내인 hint는 형식이나 사용 목적을 설명합니다. 오류 설명은 지금 제출할 수 없는 이유와 수정 방법을 전달합니다.

| 역할       | 이메일 폼에서의 문구                                   | 표시하는 시점               |
| ---------- | ------------------------------------------------------ | --------------------------- |
| 이름       | 이메일 주소 (필수)                                     | 항상                        |
| 사전 안내  | 예: name@example.com                                   | 입력하기 전부터             |
| 빈 값 오류 | 이메일 주소를 입력해 주세요.                           | 제출 시 비어 있을 때        |
| 형식 오류  | 이메일 주소를 name@example.com 형식으로 입력해 주세요. | 제출 시 형식이 맞지 않을 때 |

자리표시자인 `placeholder`만으로 이름을 대신하면, 입력이 시작되는 순간 안내가 사라집니다. 눈에 보이는 이름을 유지하고, 입력란의 `id`와 `label`의 `for`를 연결합니다. 그러면 이름을 눌러 입력란으로 이동할 수 있고 보조 기술도 둘의 관계를 파악할 수 있습니다.

잘못된 입력을 빨간 테두리로만 표시하는 것도 부족합니다. 색을 구분하기 어렵거나 화면을 읽어 주는 프로그램을 사용하는 사람에게는 오류 이유가 전달되지 않습니다. [WCAG 2.2의 오류 식별 기준 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)은 자동으로 찾은 입력 오류의 항목과 이유를 글로 설명하도록 요구합니다. [수정 제안 기준 3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)은 보안이나 서비스 목적을 해치지 않는 범위에서 알고 있는 수정 방법도 안내하도록 설명합니다.

## 제출 실패 후 돌아오는 길을 만듭니다

입력란 옆의 오류는 수정할 때 읽기 좋습니다. 다만 긴 폼에서 화면 밖에 있는 오류를 찾으려면 전체를 다시 훑어야 합니다. 폼 위에 오류 요약을 두고 해당 입력란으로 가는 링크를 제공하면 이 이동을 줄일 수 있습니다.

여기서 포커스는 키보드 입력이 향하는 위치입니다. 오류 요약에 `tabindex="-1"`을 주면 일반적인 Tab 이동 순서에는 추가하지 않으면서 코드로 포커스를 옮길 수 있습니다. 요약의 링크를 누르면 문제 입력란으로 돌아옵니다. [GOV.UK Design System의 오류 요약](https://design-system.service.gov.uk/components/error-summary/)도 요약으로의 포커스 이동, 입력란 링크, 요약과 개별 오류 문구의 일치를 권장합니다. 모든 폼에 요약이 있어야 한다는 WCAG의 일괄 규정으로 해석할 필요는 없습니다.

처음 폼을 열었을 때부터 오류를 표시하지는 않습니다. 아래 예제는 제출할 때 검사하며, 수정 중에는 포커스를 빼앗지 않습니다. 다시 제출하면 현재 값으로 재검사합니다. 글자를 하나 입력할 때마다 “오류”를 알리는 방식은 아직 작성 중인 사람에게 불필요한 중단을 만들 수 있습니다.

## 이메일 폼으로 구현해 봅니다

같은 폴더에 `form.html`과 `form.mts`를 만듭니다. HTML에는 CSS 없이도 의미가 남는 기본 요소를 사용합니다. 입력 그룹을 처음에는 비활성화해 스크립트 미로딩 때 기본 GET 제출이 일어나지 않도록 합니다. `novalidate`는 브라우저의 기본 제출 차단과 팝업 안내를 끄기 위한 속성입니다. `required`와 `type="email"`이 정의하는 입력 조건은 남아 있어 코드에서 검사할 수 있습니다.

```html filename="form.html" part="1/1"
<!doctype html>
<html lang="ko">
    <head>
        <meta charset="utf-8" />
        <meta name="viewport" content="width=device-width, initial-scale=1" />
        <title>이메일 입력 오류 실험</title>
    </head>
    <body>
        <main>
            <h1>이메일 입력 오류 실험</h1>
            <p>입력 형식만 확인하는 예제입니다. 서버로 전송하지 않습니다.</p>
            <section
                id="error-summary"
                tabindex="-1"
                aria-labelledby="error-title"
                hidden
            >
                <h2 id="error-title">입력 내용을 확인해 주세요</h2>
                <ul>
                    <li><a id="error-link" href="#email"></a></li>
                </ul>
            </section>
            <p id="init-message">
                스크립트가 준비되면 입력할 수 있습니다. 계속 비활성 상태라면
                form.mjs 파일을 확인해 주세요.
            </p>
            <form id="email-form" novalidate>
                <fieldset id="email-fields" disabled>
                    <legend>이메일 입력</legend>
                    <label for="email">이메일 주소 (필수)</label>
                    <p id="email-hint">예: name@example.com</p>
                    <p id="email-error" hidden></p>
                    <input
                        id="email"
                        name="email"
                        type="email"
                        required
                        autocomplete="email"
                        aria-describedby="email-hint"
                    />
                    <button type="submit">입력 형식 확인</button>
                </fieldset>
            </form>
            <p id="result" role="status"></p>
        </main>
        <script type="module" src="./form.mjs"></script>
    </body>
</html>
```

TypeScript는 네 부분을 순서대로 이어 `form.mts`에 저장합니다. 첫 부분은 요소를 가져오고, 기대한 HTML이 있는지 실행할 때 확인합니다.

```ts filename="form.mts" part="1/4"
const form = document.querySelector('#email-form')
const email = document.querySelector('#email')
const summary = document.querySelector('#error-summary')
const error = document.querySelector('#email-error')
const link = document.querySelector('#error-link')
const fields = document.querySelector('#email-fields')
const initMessage = document.querySelector('#init-message')
const result = document.querySelector('#result')

if (
    !(form instanceof HTMLFormElement) ||
    !(email instanceof HTMLInputElement) ||
    !(summary instanceof HTMLElement) ||
    !(error instanceof HTMLElement) ||
    !(link instanceof HTMLAnchorElement) ||
    !(fields instanceof HTMLFieldSetElement) ||
    !(initMessage instanceof HTMLElement) ||
    !(result instanceof HTMLElement)
) {
    throw new Error('예제 HTML의 요소를 확인해 주세요.')
}
```

다음은 이메일의 입력 조건을 검사하고 오류를 표시하는 부분입니다. `validity`는 브라우저가 HTML 입력 조건에 따라 제공하는 결과입니다. 빈 값과 형식 오류를 구분하지만, 계정의 실존이나 소유 여부까지 확인하지는 않습니다. 점이 포함된 도메인만 허용하는 별도 정규식도 추가하지 않았습니다.

```ts filename="form.mts" part="2/4"
function getEmailError(input: HTMLInputElement): string {
    if (input.validity.valueMissing) return '이메일 주소를 입력해 주세요.'
    if (input.validity.typeMismatch) {
        return '이메일 주소를 name@example.com 형식으로 입력해 주세요.'
    }
    return ''
}

const showError = (message: string): void => {
    error.textContent = message
    link.textContent = message
    error.hidden = false
    summary.hidden = false
    email.setAttribute('aria-invalid', 'true')
    email.setAttribute('aria-describedby', 'email-hint email-error')
    result.textContent = ''
    summary.focus()
}
```

오류가 나면 `aria-invalid`로 오류 상태를, `aria-describedby`로 사전 안내와 오류 문구의 위치를 연결합니다. 아래에서는 통과한 오류 상태를 지우고, 요약 링크를 눌렀을 때 입력란으로 이동합니다. 값을 편집하면 이전 성공 문구만 지워 아직 새 값을 확인하지 않았음을 드러냅니다. 입력 중 오류를 반복해서 알리거나 포커스를 옮기지는 않습니다.

```ts filename="form.mts" part="3/4"
const clearError = (): void => {
    error.hidden = true
    summary.hidden = true
    error.textContent = ''
    link.textContent = ''
    email.removeAttribute('aria-invalid')
    email.setAttribute('aria-describedby', 'email-hint')
}

link.addEventListener('click', (event) => {
    event.preventDefault()
    email.focus()
})

email.addEventListener('input', () => {
    result.textContent = ''
})
```

마지막 부분에서 기본 전송을 막는 리스너를 설치하고 검증 결과를 표시합니다. 모든 준비가 끝난 뒤에만 입력 그룹의 `disabled`를 해제합니다. 모듈이 로드되지 않거나 초기화 중 오류가 나면 입력과 제출이 비활성 상태로 남습니다. 이 잠금은 서버에 전송하지 않는 학습 예제를 위한 장치이며, 실제 서비스에서는 정상적인 서버 제출 경로와 JavaScript가 없는 경우의 경험을 함께 설계해야 합니다.

```ts filename="form.mts" part="4/4"
form.addEventListener('submit', (event) => {
    event.preventDefault()
    const message = getEmailError(email)
    if (message) {
        showError(message)
        return
    }
    clearError()
    result.textContent =
        '로컬 입력 형식 확인을 마쳤습니다. 서버에는 전송하지 않았습니다.'
})

fields.disabled = false
initMessage.hidden = true
```

`role="status"`는 결과 영역의 변화를 포커스를 옮기지 않고 보조 기술에 전달하도록 돕습니다. 자체적으로 검증하거나 실제 음성 안내를 보장하는 기능은 아닙니다. 오류 요약은 직접 포커스를 받으므로 상태 메시지와 같은 방식으로 처리해야 하는 것도 아닙니다. [WCAG 상태 메시지 설명](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)을 함께 참고하시면 좋습니다.

## 브라우저에서 실행합니다

TypeScript와 Python 3을 사용할 수 있는 환경에서는 다음 명령으로 컴파일하고 같은 폴더를 HTTP로 열 수 있습니다. `.mts`의 출력인 `form.mjs`를 HTML에서 그대로 불러옵니다. `npx`는 필요한 TypeScript 도구가 없으면 설치를 요청할 수 있습니다.

```sh
npx --package typescript tsc form.mts --target ES2022 --module NodeNext --lib ES2022,DOM --strict
python3 -m http.server 8080 --bind 127.0.0.1
```

`http://127.0.0.1:8080/form.html`을 열고 빈 값으로 제출, `hello`를 입력해 제출, `name@example.com`으로 수정해 제출하는 순서로 살펴봅니다. 오류가 있으면 요약으로 포커스가 이동하고 그 링크를 통해 이메일 입력란으로 돌아올 수 있습니다. 작성한 값을 지우는 `reset()`은 호출하지 않습니다. 키보드로도 Tab을 눌러 제출 버튼에 이동한 뒤 Enter로 제출해 보세요. 오류 요약에 포커스가 옮겨지면 Tab으로 요약 링크에 이동해 Enter를 누릅니다. 입력란에서 내용을 고친 뒤 다시 제출하는 흐름까지 확인합니다.

## 예제에서 확인한 흐름

2026년 11월 2일 데스크톱 Chromium에서 빈 값으로 제출했을 때 오류 요약으로 포커스가 이동했습니다. Tab으로 요약 링크에 이동한 뒤 Enter를 누르니 이메일 입력란으로 돌아갔습니다. 형식이 잘못된 주소를 제출했을 때도 입력 내용이 화면에 남았고, 요약과 입력란 옆의 오류 문구가 일치했습니다.

형식을 고쳐 다시 제출하면 오류 요약과 개별 오류가 숨겨지고 `aria-invalid`가 제거됐습니다. `aria-describedby`에는 원래의 사전 안내만 남았으며, 입력값을 비우지 않고 로컬 형식 확인 문구를 표시했습니다. 성공 후 값을 다시 편집하면 이전 결과 문구가 지워지는 것도 확인했습니다. 같은 형식 오류를 연속 제출해도 설명 연결이 중복되지 않았습니다.

스크립트 요소를 제거한 조건과 모듈 파일이 404인 조건에서는 입력란과 제출 버튼이 비활성으로 남았고, 키보드 입력으로 기본 제출이 발생하지 않았습니다. 이는 모듈이 준비되지 않은 두 조건을 확인한 결과입니다. 브라우저의 JavaScript 설정 자체를 끄거나 스크린 리더의 실제 음성 안내를 검사한 것은 아니며, 서버 제출도 포함하지 않았습니다.

## 서버에서 거절한 요청도 입력 맥락을 유지합니다

브라우저 검사는 입력한 자리에서 빠르게 고칠 수 있다는 장점이 있습니다. 다만 사용자가 JavaScript를 끄거나 HTML 제약을 바꿀 수 있으므로 서버에서도 받은 값을 검증해야 합니다. 저장할 수 있는 값인지, 해당 작업을 할 권한이 있는지도 서버가 판단합니다.

서버가 이메일 형식을 거절했다면 해당 입력란에 오류를 연결합니다. 통신이 끊겼거나 서버에 장애가 생긴 경우에는 올바른 이메일을 오류로 표시하면 사용자가 불필요한 수정을 하게 됩니다. “요청 결과를 확인하지 못했습니다. 입력 내용은 유지됩니다”처럼 확인할 수 있는 상태를 설명하고, 다시 시도할 방법을 제공합니다. 재시도에 따른 중복 등록을 막는 설계도 함께 필요합니다.

요청을 보내자마자 폼을 비우면 실패했을 때 처음부터 입력해야 합니다. 응답을 확인할 때까지 값을 유지하고, 사용자가 새로 고친 값에 이전 요청의 결과가 뒤늦게 덮어씌워지지 않도록 처리합니다. 비밀번호 같은 민감한 값을 저장소에 영구 보관해야 한다는 뜻은 아닙니다. 화면에서 입력을 유지하는 일과 저장 기간을 늘리는 일은 따로 판단합니다.

## 정리

폼의 오류 처리를 검토할 때는 제출부터 재제출까지 따라가 봅니다. 오류를 알아차리고 이유를 이해한 뒤, 입력란으로 돌아가 원래 작성한 내용을 고칠 수 있는지 확인합니다. 이번 예제는 그 이동을 작은 코드로 구성했습니다.

실제 제품에 적용할 때에는 키보드 조작에 더해 사용하는 스크린 리더에서도 확인해야 합니다. 포커스 이동을 확인한 것만으로 음성 안내의 품질까지 보장할 수는 없습니다. 이 예제만으로 폼 전체의 WCAG 적합을 판정할 수도 없습니다. 여러 입력란, 번역된 문구, 응답이 늦은 요청은 실제 제품에서 더 검증할 범위입니다.
